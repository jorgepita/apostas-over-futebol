# Dashboard

This document describes the Football Bot dashboard in technical detail. For system architecture, data flows, and component interactions, see `01_Architecture.md` and `02_Data_Flow.md`. This document focuses exclusively on the frontend.

---

## 1. Dashboard Overview

`index.html` is a single self-contained HTML file. It is the operational interface for the entire betting system: it displays picks, manages manual bets through their complete lifecycle, presents analytics, and controls bankroll settings.

**The dashboard owns:**
- The in-memory `state` object and its rendering pipeline.
- The `localStorage` copy of `cloud_state.json`.
- The user's interaction with manual bets (create, approve, reject, settle manually).

**The dashboard does not own:**
- Any file on GitHub. It cannot commit to the repository.
- The canonical state of manual bets — that belongs to `cloud_state.json` on GitHub. `localStorage` is a working copy.
- Settlement logic. Settlement runs on the backend (`update_results.py`).
- Pick generation. Picks are generated by the Python pipeline and consumed as CSVs.

**Language:** All user-facing strings are in Portuguese (PT-PT).

## 2. Application Structure

The application is a vanilla JavaScript SPA inside a single HTML file. There is no framework, no build step, and no module system. All code runs in a single `<script>` block at the bottom of the `<body>`.

### Key constants and globals

```javascript
const API_URL = 'https://apostas-over-futebol-production.up.railway.app';

const URLS = {
  footballDaily:      'https://raw.githubusercontent.com/.../picks_hoje_github.csv',
  footballBtts:       'https://raw.githubusercontent.com/.../picks_btts.csv',
  footballHistory:    'https://raw.githubusercontent.com/.../picks_history.csv',
  manual:             'https://raw.githubusercontent.com/.../manual_bets.csv',
  leagueStatsRemote:  'https://raw.githubusercontent.com/.../league_stats.csv'
};

const STORAGE_KEYS = { /* see Section 11 */ };
```

Module-level flags:

| Flag | Purpose |
|---|---|
| `autoSaveInFlight` | True while a `POST /save` is in progress; prevents concurrent saves |
| `hasPendingCloudChanges` | True if local state has not yet been saved to the cloud |
| `initialLoadDone` | True after the first `loadData()` completes |
| `_autoSaveTimer` | Debounce handle for the 4-second auto-save |
| `_dirtyGeneration` | Counter that increments on every `markDirty()`; detects in-flight changes |
| `_settlementRunning` | True while a settlement request is pending |
| `_settlementMessage` | Status text shown on the Run Settlement button |

### Rendering pipeline

```
User action / interval tick
        │
        ▼
  state mutation
        │
        ▼
  markDirty()          ← schedules cloud save (4s debounce); invalidates the
                          data-layer cache (Phase 26.39); re-renders the
                          active tab only (Phase 26.40 — see §5)
  saveLocalState()     ← writes localStorage synchronously
        │
        ▼
  rerenderAll()        ← re-renders the active tab's own panels, plus a small
                          set of deliberately-global widgets (§5)
        │
        ▼
  setActiveTab()       ← ensures the active tab is visible; also guarantees
                          a fresh render of whichever tab it switches to
```

### Event handling

Event listeners are attached once in `bindStaticButtons()`, `bindStaticInputs()`, `bindTabButtons()`, and `bindManualControls()`. All use event delegation on stable parent elements to avoid rebinding after re-renders. `rerenderAll()` and `setActiveTab()` both call `bindBotTableControls()` and `bindManualControls()` at the end to attach handlers to newly rendered table rows.

## 3. Global State

The `state` object is the single source of truth for all in-memory data. It is initialised with empty/null values and populated by `loadLocalState()` and `loadData()` during `boot()`.

```javascript
const state = {
  footballDaily:     [],    // today's bot picks (merged from daily + BTTS CSVs)
  footballHistory:   [],    // all bot picks history (picks_history.csv)
  leagueStats:       [],    // per-league stats (league_stats.csv)
  bankrollInicial:   null,  // initial bankroll amount (number or null)
  bankrollInicialSet: false,// true once bankroll is locked
  localEdits:        {},    // pickKey → {apostada, oddReal, stakeReal, resultadoManual}
  manualBets:        [],    // manual bets (cloud_state.json source)
  movements:         [],    // bankroll deposits and withdrawals
  sessionStartDate:  '',    // ISO date when current betting session started
  lastUpdated:       null,  // Date object of last loadData() call
  activeTab:         'tab-summary',
  mobileActionsOpen: false,
  cloudAvailable:    false, // true once a cloud round-trip succeeds
  providerHealth:    {}     // per-provider settlement API health (see below)
};
```

Runtime-only additions (not persisted to localStorage):

| Property | Set by | Purpose |
|---|---|---|
| `state.manualBetsRemote` | `loadData()` | Rows from `manual_bets.csv` (always empty) |
| `state.fixtures` | `loadData()` | Rows from `fixtures_today.csv` (kickoff lookup for Scout) |

### Important state properties

**`state.manualBets`**  
Array of manual bet objects loaded from localStorage at startup. Each object has: `id`, `data`, `liga`, `jogo`, `mercado`, `odd`, `stake`, `resultado`, `status` (`"pending"` / `"approved"` / `"rejected"` / `"settled"`), `notas`, `placar` (final score, e.g. `"2-1"`, populated by settlement — see `04_Backend.md` §7), `settledAt`, and optional analysis fields (`botOpinion`, `edgeAtAnalysis`, `analysisSnapshot`). **Fixture-backed bets only** (created via Scout): `kickoffUTC`, `homeTeam`, `awayTeam`, `leagueId` — immutable fixture metadata persisted once at creation time by `addManualBetFromFixture()` (Phase 26.32), never re-derived from `state.fixtures` later. `kickoffUTC` is what lets the settlement engine's `RESULT_READY_DELAY` gate apply to manual bets the same way it already applies to bot picks (see ADR-012 and `05_Known_Issues.md` SETTLEMENT-2). **Free-form bets** (the manual entry form, `addManualBet()`) never have these four fields at all — there is no fixture to source them from; this is a documented, accepted limitation, not a bug.  
`status` and `resultado` are independent axes (see ADR-012): `status` is the lifecycle (who decided what), `resultado`/`placar` is the settlement result (what actually happened). A `rejected` bet is still settled by the shared engine like any other bet — `resultado`/`lucro`/`placar` get populated — but `status` never advances past `rejected` to `settled`. This is deliberate: it is what lets `getResolvedManualBets()` (financial) and `getRejectedManualBets()` (analytical) both derive from the same array without a second field or a combined status vocabulary.  
Updated by: user actions (create, approve, reject), `_doLoadCloudState()`, `_reloadManualBetsFromCloud()`.  
Persisted by: `saveLocalState()` to localStorage; `saveCloudState()` to `cloud_state.json` via Railway. The backend may drop a duplicate bet from what was sent (see ADR-013); when it does, `saveCloudState()` detects `duplicatesRemoved` in the `/save` response and calls `_reloadManualBetsFromCloud()` to resync `state.manualBets` to the canonical, deduplicated copy.

**`state.footballDaily`**  
Array of today's bot pick rows. Populated by `loadData()` by merging `picks_hoje_github.csv` and `picks_btts.csv`. Each row is a normalised bot CSV row. Rows with missing `Data`, `Jogo`, or invalid `Odd` are filtered out.  
Used by: Daily Picks page, Pending page (for kickoff lookup), Live Center (bot rows).

**`state.footballHistory`**  
Array of all rows from `picks_history.csv`. Includes both settled and unsettled picks.  
Used by: History page, Analytics, bot vs manual comparison, bankroll calculations.

**`state.localEdits`**  
Map from `pickKey` (string built from `Data||Liga||Jogo||Mercado`) to an edit object `{apostada: bool, oddReal: string, stakeReal: string, resultadoManual: string, settlementReason?: string}`. Records user-entered execution data for bot picks.  
Updated by: user editing "Apostada", "Odd Real", "Stake Real" fields in the History page, "Aprovar" on the Daily Picks page (which sets `apostada` and, since Phase 26.33 — guard corrected Phase 26.35 — defaults `stakeReal` to the pick's "Stake rec." value whenever the existing value is not a meaningful positive stake, i.e. empty, undefined, invalid, zero, or negative; see Daily Picks below), and `manualVoidBet()` (Phase 26.43 — sets `resultadoManual: 'P'` and `settlementReason: 'manual_void'` together; see Live Center §8).  
Merged into bot pick rows by: `getRowWithLocalEdits(row)` before display and analytics.

**`resultadoManual` precedence (Phase 26.34).** `resultadoManual` (set via the History page's result dropdown, `.js-bot-resultado`, or via "Live Settle"/manual void — `liveSettle()`/`settleBotBet()`/`manualVoidBet()`) is a **temporary bridge only**, for a bot pick automated settlement hasn't resolved yet. `getRowWithLocalEdits()` always prefers a valid CSV `Resultado` (W/L/P) over `resultadoManual` once one exists; `resultadoManual` is only consulted when the CSV cell is still empty/invalid. `getDailyRowsMerged()`'s cross-file reconciliation (checking `picks_history.csv` for a result when the same row's own daily-CSV cell is empty) follows the same rule — it now wins over a stale manual override too, not only over a genuinely-pending row. A stale `resultadoManual` value is never deleted or mutated automatically (see ADR-015) — it simply stops being read once the CSV carries a real result, preserving it as an inert historical record. `edit.settlementReason` (Phase 26.43) follows the identical precedence, resolved by the same branch condition inside `getRowWithLocalEdits()` — see §8 "Bot-pick bridge case" below.

**`state.bankrollInicial`** and **`state.bankrollInicialSet`**  
Initial bankroll amount. Once `bankrollInicialSet` is true, the bankroll input is locked and cannot be changed. This prevents accidental resets.  
Used by: all profit/ROI calculations, bankroll page, Kelly stake display.

**`state.movements`**  
Array of bankroll deposit and withdrawal records `{id, date, type, amount, note}`.  
Used by: Bankroll page (movements table, evolution chart).

**`state.providerHealth`** (Phase 26.18)  
Object keyed by provider (`"api-football"`, `"football-data.org"`) → `{status: "ok"|"warning", consecutiveFailures, lastError, lastSuccessAt, lastCheckedAt}`. Copied verbatim from `cloud_state.json`'s `providerHealth` field — the backend, not the browser, decides the status. Read by `updateProviderHealthBadge()` to render `#providerHealthLabel`.  
Updated by: `_doLoadCloudState()`, `_reloadManualBetsFromCloud()` — same cloud-field-copy pattern as `state.movements` (see the SYNC-1 lesson in `05_Known_Issues.md` / `08_Change_Log.md`: any function that copies cloud fields into `state` must include every field, or the omitted one silently goes stale).

**`state.sessionStartDate`**  
ISO date string (YYYY-MM-DD) when the current betting session started. Used to scope analytics to the current session.

**`state.cloudAvailable`**  
Boolean reflecting whether the last cloud operation succeeded. Drives the cloud status indicator in the sidebar.

## 5. Rendering Architecture

**Phase 26.40 replaced "re-render every panel on every mutation" with an active-tab-gated dispatcher.** Every tab panel is still fully present in the DOM at all times (ADR-005's single-file, all-tabs-mounted model is unchanged), and every page is still fully up to date the instant it's opened — **this is not lazy-loading**. The change is purely about not doing redundant work: a page's own render functions now only run while that page is the active tab, or at the moment it becomes the active tab (which always forces a fresh render regardless of how long it's been since that tab last ran). A small, deliberately-named set of global widgets still updates on every mutation regardless of which tab is visible.

This followed directly from Phase 26.38 (H1, `getPendingCount()`) and Phase 26.39 (H2, the data-layer cache): once the underlying *data* computation was cheap, the residual per-click cost was almost entirely DOM — `rerenderAll()` was still unconditionally rebuilding roughly 50 render functions' `innerHTML` regardless of which single tab the user could actually see, and a single logical action (e.g. Approve) could trigger two overlapping full render passes (`markDirty()`'s internal render, immediately followed by the click handler's own `rerenderAll()`).

### Dependency map — `PAGE_RENDERERS`

Every render function was traced against the actual DOM element(s) it targets — not the legacy grouping the old `rerenderXOnly()` wrappers used, several of which mixed multiple tabs' content together (e.g. the old `rerenderSummaryOnly()` also rendered all of `tab-analytics` and `tab-bankroll`; `rerenderManualOnly()` also rendered `tab-pending` and `tab-live`) — and classified as belonging to exactly one tab, or GLOBAL:

```javascript
const PAGE_RENDERERS = {
  'tab-summary':     [renderTopDecisionBlock, renderSummaryHeadlineStats, renderAlertsCenter, renderOpenBets, renderSummary, renderBankrollChart, renderMobileHomeDash],
  'tab-day':         [renderFootball, syncQuickMarketButtons, renderPicksKpiRow],
  'tab-history':     [renderClosedRealTable, renderHistoryKpiRow, renderHistoryIntelligence, renderHistoryTimeline, renderHistoryEquity],
  'tab-manual':      [renderManualScout, renderManualBets],
  'tab-pending':     [renderPendingQueue],
  'tab-live':        [renderLiveCenter],
  'tab-analytics':   [renderAnalytics, renderAnalyticsPerformers, renderLeagueAnalytics],
  'tab-versus':      [],   // renderVersus() is GLOBAL — see below, deliberately not gated here
  'tab-strategylab': [renderStrategyLab],
  'tab-bankroll':    [renderBankrollPage],
  'tab-settings':    []
};
```

**Deliberate GLOBAL exception — `renderVersus()`.** It populates `window._opnSimCache`, consumed by Strategy Lab, the Recommendation Engine, Opinion Validation, and the Simulator regardless of which tab is currently active. Gating it to only run while `tab-versus` is active broke all four of those pages (caught by a failing regression during this phase's own validation — `test_strategylab.js`'s "Compare Against Production" check). It now runs unconditionally inside `rerenderAll()` on every call; its measured cost is negligible (~0.18–0.22s even on the real, full-scale account), so it was kept as one explicit, documented exception rather than refactoring the cache to be lazily computed per-consumer.

### Dispatcher functions

```javascript
function renderActiveTabContent(tabId) {
  (PAGE_RENDERERS[tabId] || []).forEach(fn => {
    try { fn(); } catch (e) { console.error(fn.name || tabId, e); }
  });
  _lastRenderedTab = tabId;
  _lastRenderedAtDataGeneration = _dataGeneration;
}

function renderActiveTabIfStale(tabId) {
  if (_lastRenderedTab === tabId && _lastRenderedAtDataGeneration === _dataGeneration) return;
  renderActiveTabContent(tabId);
}
```

`renderActiveTabIfStale()` is what eliminates duplicate render passes for one logical user action: it reuses the Phase 26.39 `_dataGeneration` counter (bumped by `invalidateDataCache()` on every real state mutation) as its "has anything actually changed" signal, rather than a fragile standalone boolean — so it can never skip a render that would leave stale data on screen. It is called from three places (`markDirty()`, `rerenderAll()`, `setActiveTab()`); when two of them fire back-to-back for the same click, the second call becomes a no-op.

### `rerenderAll()`

```javascript
function rerenderAll() {
  fillFilters();
  renderActiveTabIfStale(state.activeTab);          // active tab's own panels only
  try { renderVersus(); } catch (e) { /* ... */ }    // GLOBAL — see above
  bindTabButtons();
  bindQuickMarketButtons();
  updateApostasButton();
  updateApostasTooltip();
  applyBankrollImmutability();
  setActiveTab(state.activeTab, { scrollToTop: false });
  bindBotTableControls();
  bindManualControls();
}
```

Still the function called after any data change that isn't a live-input edit. It no longer unconditionally rebuilds every tab's DOM — only the active tab's own panels (deduped against `_dataGeneration`), plus the deliberately-global `renderVersus()`. Every render call remains wrapped in a try-catch — a failure in one panel does not prevent others from rendering.

### `markDirty(skipRender = false)`

```javascript
function markDirty(skipRender = false) {
  invalidateDataCache();
  _dirtyGeneration++;
  hasPendingCloudChanges = true;
  updateCloudStatus();
  if (!skipRender) renderActiveTabIfStale(state.activeTab);
  clearTimeout(_autoSaveTimer);
  _autoSaveTimer = setTimeout(() => { /* saveCloudState() after 4s */ }, 4000);
}
```

`markDirty()` now also dispatches a render of the active tab (previously it had no rendering responsibility at all — callers relied on a separate `rerenderAll()`/`rerenderXOnly()` call for that). `skipRender = true` is used by the Pending page's two live-input handlers (`.js-odd-real`/`.js-stake-real`, edited via `bindBotTableControls()`'s inner `update(key, changes, rerender, skipActiveTabRender)`): those inputs render only while `tab-pending` is active, so without this flag a render on every keystroke would destroy and recreate the very input being typed into, losing focus and cursor position mid-edit — a regression this phase's own validation caught (`test_h2_cache_correctness.js`). Live edits still invalidate the cache and schedule the cloud save; they simply don't force an immediate DOM rebuild of their own page while the user is actively typing in it.

### Tab activation — `setActiveTab(tabId, {scrollToTop=true}={})`

`setActiveTab()` shows the tab panel matching `tabId`, hides all others, and now always guarantees a fresh render of the destination tab:

```javascript
try { renderActiveTabIfStale(tabId); } catch (e) { console.error(tabId, e); }
bindBotTableControls();
bindManualControls();
```

A switch to a different `tabId` never matches `_lastRenderedTab`, so `renderActiveTabIfStale()` always renders on activation — this is what makes the model **not** lazy-loading: a page is fully current the instant it's opened, whether it was rendered a second ago or has been stale since the session started. `bindBotTableControls()`/`bindManualControls()` re-run after every activation, since a freshly-rendered tab's DOM needs its click/input handlers rebound (`.onclick =` / `.oninput =` property assignment — confirmed idempotent, rebinding overwrites rather than stacking listeners). Tab switching still does not trigger `loadData()` or any network call.

### Superseded partial renderers

An independent architecture audit (Phase 26.41) found that Phase 26.40 had left the entire Manual Bets mutation surface (`addManualBetFromFixture()`, `mbHandleRowAnalyze()`, `mbHandleRowSave()`, `mbHandleRowApprove()`, `mbHandleRowReject()`) and two Bankroll movement handlers (`addMovement()`, delete-movement) still calling a legacy wrapper or a redundant direct render alongside `markDirty()` — the exact "two overlapping render passes" / "rebuild invisible DOM" problem H3 was built to eliminate, just in a part of the file the original H3 migration hadn't reached. Phase 26.41 migrated all 7 of those mutation paths to `markDirty()` alone (identical to how `.js-bot-approve` has always worked), and deleted the three wrapper functions confirmed to have zero remaining callers.

Current state: `rerenderDayOnly()` and `rerenderHistoryOnly()` remain defined and are still called directly from their own page's filter/search/sort/view-toggle controls (Daily Picks' search/league/market/result filters; History's search/source/date/league/market/result/odds filters and the Resolvidas/Rejeitadas toggle) — a deliberate, pre-existing, UI-only pattern (no `markDirty()` involved, since no state mutation occurs) that predates H1/H2/H3 and is unrelated to it; not migrated, per the audit's explicit instruction not to touch wrappers used for filtering/sorting. `rerenderManualOnly()` remains defined and is still called from exactly two places — `mbHandleRowEdit()` and `mbHandleRowCancel()` — both of which only toggle `window._mbEditState` (a UI-only edit-mode flag, not part of `state`) and never call `markDirty()`; same category as the two filter-only wrappers above, kept for the same reason. `rerenderSummaryOnly()`, `rerenderPendingOnly()`, and `rerenderLiveOnly()` were deleted in Phase 26.41 — each had zero live callers, confirmed by a full-file caller search before removal.

### Auto-save and dirty state

After any state mutation:
1. `markDirty()` is called.
2. `hasPendingCloudChanges` is set to `true`.
3. The cloud status indicator updates to "alterações por guardar".
4. A 4-second debounce timer is set. If no further changes arrive, `saveCloudState()` runs.
5. `saveCloudState()` sends `POST /save` with the full `state` object.
6. On success, `hasPendingCloudChanges` is cleared (only if `_dirtyGeneration` has not changed during the fetch).
7. On failure, `hasPendingCloudChanges` remains `true` and a retry is scheduled.

## 6. Page-by-Page Documentation

### Home / Summary (`tab-summary`)

**Purpose:** At-a-glance overview on mobile. On desktop, this tab is also visible but the primary navigation is via the sidebar.

**Data sources:** `state.footballDaily` (today's picks count), `state.footballHistory` + `state.localEdits` (settled history for P&L summary), `state.manualBets` (manual bet counts).

**User interactions:** None. Read-only summary cards.

**Update triggers:** Any `rerenderAll()` call; tab activation on mobile.

---

### Daily Picks (`tab-day`)

**Purpose:** Shows today's bot picks that have not yet been marked as executed (`apostada = false`). Once the user marks a pick as "Apostada" (bet placed), it disappears from this view.

**Data sources:** `state.footballDaily` — merged from `picks_hoje_github.csv` (O2.5 picks) and `picks_btts.csv` (BTTS picks). Rows are filtered to remove already-approved picks (`_apostadaBool === true`).

**User interactions:**
- Filter by market (O2.5, BTTS), league, date.
- Mark a pick as "Apostada" (`.js-bot-approve`, bound in `bindBotTableControls()`) — sets `localEdits[pickKey].apostada = true`, calls `markDirty()`, `saveLocalState()`, `rerenderAll()`. **(Phase 26.33, guard corrected Phase 26.35)** In the same click, if `localEdits[pickKey].stakeReal` does not parse to a meaningful positive stake at approval time (empty, undefined, invalid string, zero, or negative — checked via `num()`, not string truthiness), it is defaulted to the row's displayed "Stake rec." value (`computeRecommendedStake(row).value` — the same dynamic recommendation shown in that pick's own "Stake rec." column, not the raw "Stake mod." Kelly output; this function is hard-floored at 1, so it can never itself produce zero). A genuine positive `stakeReal` the user already typed in before clicking "Aprovar" is never overwritten, and the default is applied exactly once, at the moment of approval — editing "Stake Real" afterward on the History page works exactly as before. See `05_Known_Issues.md` DASHBOARD-5 for why the original empty-string check was insufficient. **(Phase 26.46)** Immediately before this mutation, `confirmFixtureApprovalExposure()` checks whether another approved bet already exists on the same fixture (any market, bot or manual) and, if so, shows a PT-PT confirmation before proceeding — see "Fixture-Level Approval Exposure Warning" below (ADR-019).

**Update triggers:** `loadData()` (page load, 60-second interval); any `rerenderAll()`.

**Dependencies:** `getRowWithLocalEdits()` merges `state.localEdits` into each bot row before display.

---

### Live Center (`tab-live`)

**Purpose:** Shows all active bets — both bot picks and manual bets — that are in play right now (kickoff has passed, result not yet settled).

**Data sources:**
- Manual rows: `getManualRowsMerged()` filtered for `isLocal === true`, `status === 'approved'`, resultado not in `{W, L, P}`, and kickoff ≤ now (or date ≤ today if no kickoff data). Kickoff is `resolveManualKickoff(b)` (Phase 26.42) — the bet's own persisted `kickoffUTC` (set at creation time, Phase 26.32) when present, falling back to a live `fixtures_today.csv` lookup only for older bets that predate that persistence.
- Bot rows: `state.footballDaily` rows where `apostada === true` and result not settled, or history rows for today.

**User interactions:**
- "Run Settlement" button — `POST /run-settlement` to Railway; calls `_reloadManualBetsFromCloud()` on response.
- Manual settle buttons (W/L/P) — marks the bet as settled locally; calls `markDirty()`.

**Update triggers:** Any `rerenderAll()` or `rerenderLiveOnly()` call.

**`getLiveRows()` filter (manual bets):**
```javascript
b.isLocal === true
&& b.status === 'approved'
&& !['W','L','P'].includes(b._resultKey)
&& b.data exists
&& (kickoffMs !== null ? kickoffMs <= Date.now() : b.data <= today)
```

---

### Pending (`tab-pending`)

**Purpose:** Shows approved bets (both bot picks and manual bets) whose kickoff has not yet arrived. These bets are ready to watch but not yet "live".

**Data sources:** `getPendingRows()` merges two disjoint row shapes into one array — manual bets from `getManualRowsMerged()`, and bot picks from `getAllBotRowsMergedUnique()`. Manual kickoff is `resolveManualKickoff(b)`, identical to Live Center above:

```javascript
// manual: b.isLocal === true && b.status === 'approved'
//   && (kickoffMs !== null ? kickoffMs > Date.now() : b.data > today)
// bot:    r._apostadaBool && !['W','L','P'].includes(r._resultKey)
//   && (kickoffMs !== null ? kickoffMs > Date.now() : normalizeDateString(r['Data']) > today)
```

Both branches sort together by date ascending. `renderPendingQueue()` and `buildPendingCardHtml()` are the only consumers of the full row list. Callers that only need the count — `computeAlerts()`'s "Muitas apostas abertas" threshold and the Home/Summary KPI (`renderSummaryHeadlineStats()`, `renderMobileHomeDash()`) — use `getPendingCount()` instead (Phase 26.38): a lightweight helper mirroring the same two filter predicates without the `.map()` step, so it never triggers `computeRecommendedStake()`'s per-row cost. The two are mathematically guaranteed to agree (`getPendingCount() === getPendingRows().length`) since the filters are identical; see `08_Change_Log.md` Phase 26.38.

**Displayed "Stake" column (`Phase 26.36`, header wording corrected `Phase 26.37`):** the two row types show different concepts under one shared desktop column, since manual bets have no model/recommended/real split:
- **Manual rows** — `.stake = b.stake`, the bet's own single entered stake. Unchanged since this page's inception.
- **Bot rows** — `.stake = computeRecommendedStake(r).value` (the same function and value Daily Picks' own "Stake rec." column and the Phase 26.33/26.35 approval auto-fill use) — **not** the raw model stake (`r._stakeModeloNum`, "Stake mod." on Daily Picks), which Pending showed prior to Phase 26.36. Once a pick is approved, the raw model stake is no longer the operationally relevant figure; this value is directly comparable to the adjacent "Stake Real" column — equal values mean the recommendation was followed, a difference means the user deliberately adjusted the stake.

**Header/label wording (`Phase 26.37`):** the desktop table's `<th>` reads plain **"Stake"** — Phase 26.36 briefly renamed it to "Stake rec.", but that single header also sits above manual rows, for which "recommendation" is not an accurate description of their own entered stake; "Stake" is deliberately neutral ("the operational stake associated with this pending bet"), true for both row types. The mobile card is more precise, since its label is computed per row (`buildPendingCardHtml()`'s `stakeLabel`): `'Stake rec.'` for bot rows, `'Stake'` unchanged for manual rows — no shared-header caveat there. Only the desktop label changed between Phase 26.36 and 26.37; the underlying bot-row **value** (`computeRecommendedStake()`) has been the same since Phase 26.36.

**User interactions:**
- "Cancelar" button — for manual bets, rejects a pending bet (status back to a rejected state); for bot picks, sets `apostada = false` via `pendingCancel()` (the pick returns to Daily Picks as unapproved). In both cases calls `markDirty()`. `pendingCancel()` deliberately does not clear a bot pick's `stakeReal`/`oddReal` — see `05_Known_Issues.md` DASHBOARD-5 for why a stale value surviving a cancel mattered.
- Bot rows also expose inline "Odd Real"/"Stake Real" number inputs (`.js-odd-real`/`.js-stake-real`, bound in `bindBotTableControls()`) — the same fields editable from the History page.

**Update triggers:** Any `rerenderAll()` or `rerenderManualOnly()`.

### Manual Bets (`tab-manual`)

**Purpose:** Two functions in one tab:
1. **Scout Workspace** — search for fixtures, run the Poisson model, create manual bets.
2. **Bet list** — list of all manual bets not yet approved, with approve/reject actions.

**Data sources:**
- Scout: API-Football `/fixtures` endpoint called on-demand when the user searches.
- Bet list: `state.manualBets` filtered for `status === 'pending'`.

**User interactions:**
- Type a team name or date → `renderManualScout()` queries API-Football.
- Select a fixture → `analyzeFixture()` calls the shared `QuantEngine` module (Phase 26.29 — same formulas as the Python bot, see `01_Architecture.md` "Shared Quantitative Engine" and ADR-014) → edge and Kelly stake are computed.
- "Criar" (Create Bet) → `mbHandleCreate()` → `addManualBetFromFixture()` — pushes to `state.manualBets`, calls `markDirty()`, re-renders the Manual Bets panels. The Scout card for that fixture disappears immediately (see below) and does not require a page refresh to stay hidden.
- "Aprovar" (Approve) → sets `status: 'approved'`, calls `markDirty()`. Bet moves to Pending/Live.
- "Rejeitar" (Reject) → sets `status: 'rejected'`, calls `markDirty()`. **The bet is not removed** — it remains permanently in `state.manualBets` as an analytical record (see ADR-012). It disappears from Live Center/Pending (both require `status === 'approved'`) and from bankroll/ROI/analytics (`getResolvedManualBets()` excludes `status === 'rejected'`). It stays visible in the Manual Bets list (badge "Rejeitada") **only until settlement gives it a result** — once `resultado`/`placar` are populated, it drops out of the operational Manual Bets list automatically (Phase 26.31, correcting Phase 26.28's initial fix, which removed it from the wrong page) since it no longer needs attention there. It appears in the History page's "Rejeitadas" view (see §9) **permanently**, both before and after settlement — that page is the durable archive of rejected bets, and remains fully available to every module that reads `state.manualBets` directly (Strategy Lab, Opinion Validation, Recommendation Engine, Simulator, Bot vs Manual). Rejecting is reversible — clicking "Aprovar" on a rejected bet moves it back to `approved`, at which point it starts counting financially again.
- "Remover" (Delete) → the only action that actually removes a bet from `state.manualBets`. This is also what makes its Scout card reappear (see below).
- Manual entry form — allows creating a bet without Scout by filling fields directly; guarded by the same duplicate check as the Scout path (see below).

**Duplicate protection.** Before pushing a new bet (from either the Scout "Criar" button or the manual entry form), `findManualBetByOpportunity(data, liga, jogo, mercado)` checks whether a bet already exists for the same fixture + market, in *any* lifecycle state, using the same league/market normalisers as the rest of the app (`normalizeLeagueCode()`, `normalizeMarket()`). If found, the create is refused (inline message on the Scout card; `alert()` on the manual form) instead of pushing a second record. Because this check and the push both happen synchronously inside the same function call, a double-click cannot create two records — the second call always sees the first bet already in `state.manualBets`. The backend applies the same rule independently as an authoritative backstop (see `04_Backend.md` §4, ADR-013).

**Scout card visibility (Goal: no accidental duplicate creation).** `renderManualScout()` builds a set of fixture keys (`date_league_home_away`) from **every** bet in `state.manualBets`, regardless of `status` — pending, approved, rejected, or settled — and filters those fixtures out of the upcoming-fixtures list before rendering cards. A Scout card therefore disappears the instant "Criar" succeeds and stays hidden for as long as any bet exists for that fixture; no page refresh is needed, and no polling is involved (it is derived directly from `state.manualBets` on every render). The card only reappears once the bet is actually removed ("Remover") — approving, rejecting, or settling a bet does not bring its card back. This hide-key is deliberately per-fixture (not per-market): a Scout card covers both O2.5 and BTTS for one fixture, and creating either one hides the whole card. The finer-grained fixture+market identity used for duplicate *detection* (`findManualBetByOpportunity()`, above) is a separate, more precise check used at creation time and by the backend.

## 7. Manual Bets Workspace

The complete lifecycle of a manual bet in the dashboard:

### Step 1 — Fixture Search (Scout)

The user types a team name or date into the Scout search field. `renderManualScout()` calls the API-Football fixtures endpoint. Results are shown as fixture cards with team names, league, date, and kickoff.

### Step 2 — Quantitative Analysis (Phase 26.29)

The user clicks a fixture card. `analyzeFixture()` (in `index.html`) runs:
- Loads `config.json` once per session (`loadModelConfig()`, cached, fetched from GitHub raw — falls back to a frozen default if the fetch fails) so the window/decay/min-games/lambda-boost/BTTS-adjustment values are the exact same ones the Python bot uses, not a hand-maintained copy.
- Fetches the league's `data_raw/{league}.csv` history (`loadLeagueHistory()`, cached per league) to get `λ_home`/`λ_away` via `QuantEngine.computeLambdas()` — the same function (mirrored from `src/calculations.py::compute_lambdas()`) the bot's pick generation uses.
- Calls `QuantEngine.probOver25()`/`probBttsDiagnostics()`, `.kellyFraction()`, `.confidenceFactor()`, `.fairOdds()`, `.expectedValue()` — every quantitative value (`ProbModel`, `ProbMarket`, `Edge`, `Confidence`, `KellyTrue`, `fairOdd`, `EV`) comes from this shared module, not from formulas maintained separately in the dashboard.
- **Only after** the quantitative result is computed does the decision layer run: `computePickScore()` (heuristic 0–100 Score) and `classifyManualOpinion()` (STRONG BUY/BUY/NEUTRAL/AVOID) — both consume the QuantEngine output and remain outside it, per ADR-014.
- Displays edge, Kelly fraction, recommended stake, and a verdict (value / no value).

Analysis result is stored in the bet object as `botOpinion`, `edgeAtAnalysis`, `scoreAtAnalysis`, `analysisSnapshot`.

### Step 3 — Bet Creation

The user fills in market, odd, stake (pre-filled from Scout analysis if applicable) and clicks "Criar Aposta".

`addManualBet()` is called:
```javascript
state.manualBets.push({
  id: makeManualId(),       // unique ID: timestamp + random suffix
  data, liga, jogo, mercado, odd, stake, resultado: '',
  status: 'pending',        // initial state
  analysisStale: false,
  // analysis fields if Scout was used
});
markDirty();               // schedules cloud save
```

The bet is immediately visible in the Manual Bets list with status "pending".

### Step 4 — Approval

The user clicks "Aprovar" (Approve) on the bet in the Manual Bets list. **(Phase 26.46)** `mbHandleRowApprove()` first calls `confirmFixtureApprovalExposure()` — if another approved bet already exists on the same fixture (any market, bot or manual), a PT-PT confirmation appears before the mutation below runs; Cancel leaves the bet untouched. See "Fixture-Level Approval Exposure Warning" after this section (ADR-019).

```javascript
state.manualBets[idx].status = 'approved';
markDirty();
rerenderAll();
```

The cloud auto-save fires within 4 seconds. The bet transitions:
- Removed from the Manual Bets "pending" list.
- Appears in **Pending** (if kickoff has not yet passed).
- Appears in **Live Center** (if kickoff has passed).

### Step 5 — Rejection

The user clicks "Rejeitar" (Reject). `status` is set to `'rejected'`; the bet is **not** removed from `state.manualBets`. `markDirty()` is called. The bet disappears from Pending/Live Center (both require `status === 'approved'`) and from every financial calculation (`getResolvedManualBets()` excludes it — see ADR-012). It becomes visible in the operational Manual Bets list and in the History page's "Rejeitadas" view (§9) **while unsettled**. It still passes through settlement like any other bet (Step 8) — its fixture's real result, final score, and theoretical profit get populated exactly as if it had been approved — the only difference is that none of that ever reaches bankroll/ROI. Once settled, it drops out of the operational Manual Bets list (Phase 26.31 — it no longer needs attention there) but **remains permanently visible in "Rejeitadas"** (the durable archive) and fully available to Strategy Lab, Opinion Validation, and every other analytical module that reads `state.manualBets` directly. Rejection is reversible: approving a rejected bet moves it back to `approved` and it starts counting financially again.

### Step 6 — Persistence

After every create/approve/reject:
1. `saveLocalState()` writes to localStorage synchronously.
2. `markDirty()` schedules `saveCloudState()` after 4 seconds.
3. `saveCloudState()` sends `POST /save` to Railway with the full `state` object.
4. Railway writes `cloud_state.json` to GitHub.

The cloud status indicator reflects the save state in real-time.

### Step 7 — Live Center

After kickoff passes, `getLiveRows()` includes the bet. It appears in the Live Center alongside any active bot picks.

### Step 8 — Settlement

Settlement can be triggered:
- **From the dashboard:** User clicks "Run Settlement" → `POST /run-settlement` → Railway runs `run_settlement_remote()` → result written to `cloud_state.json` → `_reloadManualBetsFromCloud()` pulls the result back into `state.manualBets` → `rerenderAll()`.
- **Externally (GitHub Actions):** `cloud_state.json` is updated on GitHub. The browser is not notified. The user must click "Load Cloud" to see the result.

### Step 9 — History

After settlement, `resultado` is W/L/P. `getManualRowsMerged()` returns the bet with `_resultKey` in `{W, L, P}`. It is excluded from the Live Center and Pending filters. It appears in the History page and feeds Analytics and Bankroll calculations.

### State Transition Summary

Lifecycle (`status`) and settlement result (`resultado`/`placar`) are independent axes (ADR-012). The diagram below shows both branches; settlement (the bottom half) runs identically regardless of which branch a bet is on — the only difference is what it's allowed to affect afterwards.

```

   status: 'pending'
   resultado: ''
      │
      ├─ user clicks Aprovar ──────────────┐
      │                                    ▼
      │                         [approved, pre-kickoff]
      │                            status: 'approved'
      │                            → appears in Pending
      │                                    │

      │                                    ▼

                │ settlement writes   status: 'approved' (unchanged by settlement)
```

A rejected bet can be re-approved at any point (before or after settlement) by clicking "Aprovar" again; it then behaves exactly like any other approved bet, including counting financially if it already carries a settlement result.

### Fixture-Level Approval Exposure Warning (Phase 26.46, ADR-019)

Both approval mutations — Daily Picks' `.js-bot-approve` handler and Manual Bets' `mbHandleRowApprove()` — run a synchronous gate, `confirmFixtureApprovalExposure(data, liga, jogo, candidateStake)`, before mutating anything. It is a **warning**, not a restriction: the dashboard has always allowed more than one approved bet on the same fixture (a user may deliberately want both an Over 2.5 and a BTTS position, bot and/or manual), and this remains fully possible — the gate only makes the resulting exposure visible before it happens.

**Fixture identity.** `fixtureExposureKey(data, liga, jogo)` — `Date + League + Game`, deliberately excluding Market and Bot/Manual origin — reuses the exact same normalisers `manualBetOpportunityKey()` already established for duplicate-bet detection (`normalizeDateString()`, `normalizeLeagueCode()`, a lowercase-folded `Jogo`) minus the market component. This is a dashboard-local sibling of ADR-018's Python-side `fixture_id_from_*()` helpers, not a reuse of them — the dashboard has its own client-side row representations (PascalCase CSV fields for bot rows, lowercase `cloud_state.json` fields for manual rows) and no existing JS fixture-only identity to reuse. `normalizeLeagueCode()`'s exact-map lookup (no fuzzy matching) keeps MLS and MLS Next Pro distinct.

**What counts as existing exposure.** `getApprovedFixtureExposure(fixtureKey)` returns every *other* bet, bot or manual, currently `approved AND unresolved` on that fixture — reusing the identical predicates `getRiskMetrics()`'s `stakeOpen` already uses (`r._apostadaBool && r._resultKey === 'pending'` for bot rows via `getAllBotRowsMergedUnique()`; `b.isLocal && b.status === 'approved' && !['W','L','P'].includes(b._resultKey)` for manual rows via `getManualRowsMerged()`), over the same Phase 26.39 memoized arrays — no new dataset. An unapproved recommendation, a rejected/cancelled bet, and a resolved W/L/P or voided-P bet never count. Because the gate always runs *before* the mutation it guards, the candidate bet itself is provably not yet "approved" at lookup time, so it is automatically excluded with no separate self-exclusion logic.

**Logical-bet deduplication (verified, Phase 26.46's pre-commit audit).** A single logical bet cannot appear twice in the result. A bot pick legitimately exists in both `state.footballHistory` and `state.footballDaily` simultaneously (approval never removes a row from today's daily CSV), but `getAllBotRowsMergedUnique()` already collapses that to one entry by exact `_pickKey`, which holds because both arrays are normalised through the identical `normalizeBotCsvRow()`. A manual bet has no equivalent dual representation — one mutable record per `id` in `state.manualBets`; the only other merged array, `state.manualBetsRemote` (the dead `manual_bets.csv`, ADR-001), is excluded outright via `isLocal === true`. See ADR-019's Consequences for the full empirical trace.

**Warning content (PT-PT).** When exposure exists, `buildFixtureExposureConfirmMessage()` lists each existing bet's origin (Bot/Manual), game, market, odd, and stake, then the current combined exposure, the candidate's own stake (the exact value about to be persisted — including a Phase 26.33/26.35 auto-filled "Stake rec." default, if applicable), and the resulting total. Presented via the browser-native `confirm()` — the dashboard has no reusable modal/dialog component (confirmed by audit; `manualVoidBet()`'s "Anular aposta" already uses the same pattern), so this is the smallest architecture-consistent choice rather than a new UI system.

**Cancel / Confirm semantics.** Cancel returns from the click handler before either `update()` (bot) or the `state.manualBets[betIdx] = {...}` assignment (manual) runs — zero mutation, verified by regression. Confirm ("Aprovar na mesma") falls through to the exact same, unmodified approval code that already ran before this phase — no parallel approval implementation exists.

**Explicitly independent from ADR-018.** ADR-018's fixture-level market lock constrains what the *bot generation pipeline* may recommend across runs (Python, `src/pipeline.py`). This gate constrains what the *dashboard warns about* at approval time (JavaScript, `index.html`). Neither reads the other's identity keys or code paths. See ADR-019 for the full architectural reasoning.

## 8. Live Center

### Data sources

`getLiveRows()` builds the unified live row list:

1. **Manual rows:** from `getManualRowsMerged()` with filter:
   ```
   isLocal === true
   AND status === 'approved'
   AND _resultKey not in {W, L, P}
   AND data field exists
   AND (kickoff timestamp ≤ now OR date ≤ today)
   ```
   The kickoff timestamp is `resolveManualKickoff(b)` (Phase 26.42): the bet's own persisted `kickoffUTC` (immutable, set at creation time by Phase 26.32) when present, falling back to a live `state.fixtures` lookup (`findFixtureKickoff()`) only for bets that predate that persistence. Before Phase 26.42, `getManualRowsMerged()` did not propagate `kickoffUTC` onto its merged rows at all, and both `getPendingRows()`/`getLiveRows()` used the live lookup unconditionally — once a fixture aged out of the rolling `fixtures_today.csv` window, this displayed "Kickoff: —" even though the correct value was sitting in `cloud_state.json` unread. See `05_Known_Issues.md` DASHBOARD-6.

2. **Bot rows:** from `getDailyRowsMerged()` and `state.footballHistory` for rows where `apostada === true` and result is not settled.

Both sets are combined and sorted by date.

### Merge process

`getManualRowsMerged()` merges two sources:
- `remoteRows` from `state.manualBetsRemote` (always empty in production; `manual_bets.csv` has no data): `isLocal: false`.
- `localRows` from `state.manualBets` (cloud-sourced bets): `isLocal: true`. Includes `kickoffUTC` (Phase 26.42), copied straight from the raw bet object — the field a fixture-backed bet persisted at creation time (Phase 26.32).

The Live Center filter is applied to the merged list. Only `isLocal: true` bets pass (`status === 'approved'` is only meaningful on local bets).

### Rendering

`renderLiveCenter()` builds an HTML table. Each row shows: date, league, game, market, odd, stake, time since kickoff.

Every row (bot and manual alike) shows the generic quick-settle W/L/P buttons (`.js-live-win`/`.js-live-loss`/`.js-live-push` → `liveSettle()` → `settleManualBet()`/`settleBotBet()`) — a manual override for when the user already knows the result and doesn't want to wait for automated settlement. This is unrestricted (available the moment a bet is Live, generic `confirm()`, no audit reason stamped) and unchanged by Phase 26.43 below.

The "Run Settlement" button is rendered in this panel. Its state is controlled by `_settlementRunning` and `_settlementMessage`.

### Manual void — "Anular aposta" (Phase 26.43, ADR-017)

A second, separately-gated action distinct from the generic quick-settle `P` button above. Each row's `voidEligible` flag (`getLiveRows()`) is `true` only when the row's kickoff timestamp is known (same `resolveManualKickoff(b)` / `r['KickoffUTC']` used elsewhere on this page) **and** `Date.now() - kickoffMs >= MANUAL_VOID_AVAILABLE_AFTER_HOURS * 3600000` — a module-level variable, frozen at the default (24h) until `loadVoidPolicyConfig()` (fired once from `boot()`) resolves the real `config.json["settlement"]["void_policy"]["manual_void_available_after_hours"]` value from the same GitHub raw-content fetch Scout's `loadModelConfig()` already uses. An unknown kickoff never qualifies — there is no reliable age to gate on.

When eligible, a button ("Anular" on desktop, "Anular aposta" on mobile) appears alongside the W/L/P controls. Clicking it (`manualVoidBet()`) shows an explicit PT-PT confirmation ("Anular esta aposta como Push (P)? A stake será devolvida e a aposta será encerrada sem lucro nem prejuízo.") and, once confirmed, calls the same `settleManualBet()`/`settleBotBet()` mutation as the generic P button — now accepting an optional `reason` argument — writing `resultado`/`resultadoManual: 'P'` **and** `settlementReason: 'manual_void'`. Financial semantics (exposure release, zero profit, no bankroll inflation) are identical to any other P — see `getRiskMetrics()`/`getBankrollState()`, unchanged by this feature. History's expandable row detail (`renderResolvedClosedRealTable()`) surfaces a PT-PT "Motivo" line (`settlementReasonLabel()`) whenever `settlementReason` is non-empty, for both manual voids and the backend's own automatic postponed/cancelled/missing-fixture voids (see `04_Backend.md` §7 "Postponed/cancelled/missing-fixture voiding").

**Bot-pick bridge case — merge point (pre-commit audit correction).** For a manually-voided bot pick, `resultadoManual`/`settlementReason` are written to `state.localEdits[key]`, but everything downstream reads the *merged* row from `getRowWithLocalEdits()` (§3, "Global State"), not `localEdits` directly. A `settlementReasonFinal` is resolved there with the exact same branch condition already used for `resultadoFinal`: while the CSV's own `Resultado` is still empty (the bridge case), the local `edit.settlementReason` is used; once the CSV has a real result, the CSV's own `SettlementReason` wins outright — even when blank, e.g. a normal `W`/`L` has no reason to show. This is deliberately tied to *which source produced the currently-displayed result*, not an independent "non-empty value wins" fallback (an initial fix attempt used the latter and left a stale "Anulada manualmente" label next to a CSV-authoritative `W` — caught by its own regression test). See ADR-017's "Correction" section.

### Settlement result messages (Phase 26.18)

`runSettlement()` distinguishes three outcomes from the `/run-settlement` response, in this order:
1. `data.updated > 0` → `✓ Settlement completed` (success, green).
2. `data.updated === 0` and `data.settlement_aborted` is true → `⚠ Settlement unavailable — {provider}: {category text}` (warning, amber). This means a provider (API-Football or football-data.org) rejected the request — plan/quota/auth/network/server error — so settlement could not run, and the empty count does not mean "no games today".
3. Otherwise → `No matches to settle.` (warning, amber). This is a genuine empty result: the provider returned real fixture data, none of it matched anything eligible for settlement right now.

`PROVIDER_HEALTH_LABELS` and `PROVIDER_HEALTH_CATEGORY_TEXT` (defined near `updateCloudStatus()`) map the backend's `provider`/`category` codes to the human-readable text shown in both this message and the health badge below. See `04_Backend.md` §7 for the backend side of this (provider error classification, `settlement_aborted`).

### Provider health badge

`#providerHealthLabel`, next to the Cloud Status badge on the Settings page ("Estado da Sessão" card), reflects `state.providerHealth` — copied from `cloud_state.json`'s `providerHealth` field on every cloud load (`_doLoadCloudState()`, `_reloadManualBetsFromCloud()`), following the same "any code that assigns cloud fields to `state` must include this field" rule established after the SYNC-1 incident. **Opinion Validation (Phase 26.20, evolved Phase 26.21).** Below the existing Opinion Performance/Calibration/Insights sections (M/N/O), an additive "Opinion Validation" section objectively measures whether the Opinion classifier (STRONG BUY/BUY/NEUTRAL/AVOID) is calibrated — i.e. whether higher-confidence opinions actually realise higher ROI. It is derived entirely from the same `opnData`/`opinionBets` already computed for M/N/O (analytics-only; no new filter, no new data source, no changes to pick generation, scoring, settlement, or persistence). M, N, and O themselves are untouched and continue to produce identical values.

- **Expected vs Actual Ranking** — the static expected order side-by-side with the four opinions sorted by yield desc (ties broken by win rate, then sample size). `yield` (profit/stake, a plain ratio) is the internal comparison metric everywhere in this section; `roi` (`= yield × 100`) remains the only thing ever displayed. Because the two are a fixed monotonic transform of each other, every comparison produces the same result today — this is future-proofing for a metric that could diverge from ROI later (e.g. if stakes become risk-weighted), not a behavioural change.
- **Calibration tolerance** — `CALIBRATION_ROI_TOLERANCE = 2` (percentage points, converted internally to a yield-scale tolerance). A pair whose gap is smaller than the tolerance is treated as a tie (half credit — same treatment as an exact tie) rather than reported as an inversion, so statistically-insignificant reversals (e.g. BUY 21.0% vs STRONG BUY 20.8%) stop producing false alarms. At tolerance = 0 the scoring is provably identical to the pre-tolerance implementation (only an exact tie counts).
- **`evaluatePairs()`** — the single function that computes, for every one of the 6 possible opinion pairs, whether it's `correct`/`equivalent`/`inverted`, its ROI difference, and its credit toward the calibration score. Both the **Opinion Calibration Score** and the **Opinion Pair Analysis** table consume this same result — no pair statistic is computed twice.
- **Opinion Calibration Score (0–100)** — weighted pairwise concordance against the 6 pairs, weighted by rank distance in the expected order (adjacent pairs weight 1, e.g. STRONG BUY vs BUY; 2-apart weight 2, e.g. BUY vs AVOID; the full span weight 3, i.e. STRONG BUY vs AVOID) — so a distant inversion costs more than an adjacent one. A pair only participates once both opinions have at least one settled bet. Labelled 90–100 Excellent, 75–89 Good, 60–74 Fair, 40–59 Poor, 0–39 Broken.
- **Opinion Pair Analysis** — a table (Expected / Obtained / Difference / Status) for all 6 pairs, built directly from `evaluatePairs()`'s output: Difference in percentage points, Status one of ✓ Correct / ≈ Equivalent (within tolerance) / ✗ Inverted. A summary line counts Correct/Equivalent/Inverted out of the evaluable total.
- **Opinion Confidence** — Very Low/Low/Medium/High/Very High based on total settled opinion-tagged bets, reusing the same 10/20/50 breakpoints already used by the Opinion Quality Score's sample factor (section N), extended with a 100+ "Very High" tier. Now shown with an explanation: total settled bets, whether all four opinion buckets have data, and the number of evaluable comparisons (reusing `evaluatePairs()`'s count — nothing new is aggregated).
- **Decision Cost** — measures what the classifier's AVOID decisions actually cost or saved. STRONG BUY and BUY are treated as "followed" (bets the model recommended and the user placed for real); AVOID is treated as "not followed". `Decision Cost` = the total profit AVOID-tagged bets would have made at their recorded stake (reusing `opnData`'s existing profit sums — no new aggregation): positive (red) means the model caused profitable opportunities to be skipped; negative (green) means it correctly avoided a loss. Displayed with Followed Profit and Avoid Profit as supporting context.
- **Opinion Trend** — one small inline-SVG sparkline per opinion, showing cumulative yield (as ROI%) after every settled bet for that opinion, auto-scaled to its own min/max range (standard sparkline practice) with the final value shown as text. Computed in the same single chronological pass as the calibration history below (one sort, one loop) — no data is replayed twice.
- **Validation Insights** — a priority-ranked list, capped at 6, every rule gated on sample size / history length so nothing is fabricated from insufficient data: trend warning (highest), calibration Broken/Poor, AVOID beating BUY/STRONG BUY, the single largest-gap "correct" pair (generalised — names whichever pair has the biggest gap, not a hardcoded one), the most notable "equivalent" (within-tolerance) pair, hierarchy-matches confirmation, a global calibration-trend insight (score over the last up-to-20 settled bets, only shown if the swing is ≥10 points), a per-opinion trend insight (the single most notable opinion's yield over its last up-to-12 settled bets, only shown if the swing is ≥5pp), small-sample caveat, and a stable-engine baseline.
- **Trend Warning** — "⚠ Opinion engine may require recalibration" appears only when AVOID's yield exceeds BUY's or STRONG BUY's by more than the calibration tolerance **and** overall confidence is Medium or above **and** both compared opinions individually meet `MIN_SAMPLE_COMPARE` — so it can never fire on a handful of AVOID bets or a statistically-insignificant lead.
- **Calibration Score Over Time** — an inline SVG line chart (same visual technique as the Bankroll evolution chart), reconstructed by replaying `opinionBets` in chronological `settledAt` order and recomputing the calibration score after each new bet, starting once all four opinions have at least one settled bet. No new persistence — recomputed at render time from existing settled data.

**Opinion Engine Recommendations (Phase 26.22).** A card below Opinion Validation ("Opinion Engine Recommendations") turns the analytics above into a deterministic, rule-based advisory layer — prescriptive, not descriptive. It is computed inside the same `if (opinionValidationEl)` scope as Opinion Validation, so every rule reads values already computed there (`calib`, `confidence`, `decisionCost`, `pairResults`/`evaluablePairs`/`correctPairs`/`equivalentPairs`/`invertedPairs`, `avoidBeatsBuy`/`avoidBeatsSB`, `historyPoints`, `trendSeries`) — nothing is a second computation of a settlement statistic. This is not AI; every recommendation is a plain `if` gate over those values.

- **Rules** (each requires `!confidenceIsLow`, i.e. ≥20 settled opinion bets, unless noted): `insufficient-data` (confidence Very Low/Low — the only rule that fires *without* the confidence gate, since it explains why every other rule is silent); `review-strong-buy` / `review-buy` (an opinion beaten by one that should rank below it, an evaluable, beyond-tolerance inversion); `increase-confidence-buy` (BUY statistically tied with STRONG BUY — the positive counterpart to `review-strong-buy`, mutually exclusive with it since one requires an `inverted` pair and the other an `equivalent` one); `review-avoid` — the four-signal recalibration case: calibration score < 75 **and** Decision Cost positive **and** AVOID beating BUY and/or STRONG BUY **and** confidence ≥ Medium, all four required simultaneously so a single metric (e.g. AVOID's ROI alone) can never trigger it; `reduce-confidence-avoid` — the softer nudge when only some of those four signals hold (mutually exclusive with `review-avoid` by construction, an `if`/`else if`); `hierarchy-healthy` (zero inverted pairs across ≥4 evaluable ones); `calibration-improving`/`calibration-deteriorating` (a 50-bet lookback over `historyPoints` — wider than Opinion Validation's own 20-bet insight window, a different derived observation from the same array, not a recomputation of it); `opinion-more-stable`/`opinion-less-reliable` (per-opinion ROI-volatility change between an early and a recent 8-bet window of `trendSeries`, requiring ≥16 bets for that opinion and a ≥30% relative change); `engine-stable` (computed last, only when no alarm-type rule fired); `no-action` (absolute fallback so the list is never silently empty).
- **Severity** — Info/Low/Medium/High/Critical, computed per rule from calibration band, confidence tier, and signal count (e.g. how many pairs are inverted, whether AVOID beats *both* BUY and STRONG BUY) — never from a single metric in isolation.
- **Evidence panel** — every recommendation carries a `[label, value]` list (Calibration Score, Decision Cost, Pairs respected, Confidence, the specific ROI comparison, ...) so it can be audited back to the same numbers shown elsewhere on the page.
- **Sorting** — by severity, highest first (stable sort; ties keep rule-evaluation order).
- **Opinion Engine Health** — one overall label (Excellent/Healthy/Needs Attention/Recalibration Recommended/Critical) derived purely from the worst severity present and whether a `review-*` rule fired — not recomputed independently, so it is always consistent with the recommendation list shown underneath it.

**Recommendation Simulator (Phase 26.23).** A card below Opinion Engine Recommendations — pure decision-support, never writes to `state`, never calls `markDirty()`/`saveLocalState()`/`saveCloudState()`, never touches model thresholds, scoring, opinion generation, settlement, bankroll, persistence, or any API. Three sliders (STRONG BUY / BUY / AVOID threshold, `-10..+10`, step 1, ephemeral `_opinionSimAdjust` — reset on page reload, never persisted) replay the same settled, opinion-tagged bets (`opinionBets`, cached by reference in `window._opnSimCache` at the end of the Opinion Validation render pass) through a parameterized copy of the real classifier from `analyzeFixture()`.

- **Classifier reproduction.** `classifySimulatedOpinion(edge, score, adj)` mirrors `analyzeFixture()`'s real rule (STRONG BUY: edge% ≥ 8 or score ≥ 75; BUY: edge% ≥ 4 or score ≥ 60; NEUTRAL: edge% ≥ 0 or score ≥ 45; else AVOID) using each bet's own stored `edgeAtAnalysis`/`scoreAtAnalysis` snapshot. **Only the edge% cutoff of each tier is adjustable** — the score-based OR-branch stays fixed at its production value, since edge (single digits) and score (0–100) are different scales and only the edge criterion maps naturally onto a small integer slider. The AVOID slider adjusts the NEUTRAL tier's entry bar (AVOID has no bar of its own in the real classifier — it's simply "failed NEUTRAL's bar"). At `adj = {sb:0, buy:0, avoid:0}` this reproduces the real classifier exactly — verified by reclassifying every historical bet and checking it lands back in its own recorded `botOpinion` bucket.
- **Replay + recompute** — `computeSimulatedSummary()` buckets `opinionBets` under the given `adj` and feeds the result through the *exact same* `statsFromBets()`, `calibrationScore()`, and `confidenceTier()` functions Opinion Validation already defined — no statistic is computed a second, independent way. Confidence is always identical between Current and Simulated, because its own definition depends only on total settled sample size, which relabeling never changes — this is stated in the UI rather than fabricating a fake per-bucket confidence metric.
- **Estimated Opinion Distribution / Calibration Score / Decision Cost / Pair Score / Confidence** — Current vs Simulated comparison cards with a directional arrow, colored green (improvement), red (regression), or grey (within a documented no-significant-change band: ±2 points for calibration, ±max(€1, 5% of current) for Decision Cost, any integer change for Pair Score).
- **Recommendation Impact** — a deterministic bullet list built only from real deltas (bucket-count % change per moved slider, calibration delta, Decision Cost delta, confidence change) — never invented text.
- **Explainability** — every calibration/decision-cost movement is traced to an actual pair-status change (`inverted→equivalent→correct` or the reverse) or an actual bucket-composition change, read directly off `evaluatePairs()`'s output for both the current and simulated data — never a generic or assumed cause.
- **Best Nearby Configuration** — `findBestNearbyConfig()` searches only ±5 around the *current* slider position (≤ 11×11×11 = 1331 combinations, each an O(N) replay), discarding any candidate that empties an opinion bucket (an empty bucket would shrink `evaluatePairs()`'s denominator and could inflate the score without a genuine ordering improvement — a correctness guard, not a performance one). Ties broken by: higher score → smaller |Decision Cost| → smallest total slider movement. Purely a suggestion — never applied to the sliders or anywhere else.
- **Performance** — the cheap parts (distribution, calibration, decision cost, pair score, impact bullets) re-render synchronously on every slider `input` event (a single O(N) pass). The Best Nearby search — the one expensive step — is debounced 150ms into its own `#simBestNearby` sub-container so a fast drag never blocks the rest of the card.
- **Safety notice** — "⚠ Simulation only. No production settings have been modified." is always visible on the card.

### Strategy Lab (`tab-strategylab`, Phase 26.24)

**Purpose:** A pure, frontend-only backtesting page — a *strategy* simulator, not a model simulator. It answers "given the settled bets already stored, what would have happened if I had followed a different betting strategy?" It has its own sidebar nav entry and tab panel, separate from Bot vs Manual. Never writes to `state`, never persists, never touches pick generation/scoring/settlement/bankroll/persistence/APIs/the Opinion engine/the Recommendation engine.

**Data foundation.** `getStrategyLabPool(seasonMode)` returns every settled, Scout-analysed manual bet (`hadAnalysis && botOpinion && resultado ∈ {W,L,P}`) for the selected season — **including rejected bets**, deliberately: a strategy backtest must be able to consider opportunities the real strategy actually passed on. Bot picks are not included (they carry no Opinion/analysis-score data in production). Season modes reuse the existing season architecture: `"current"` filters by `isOnOrAfterSession()` (the same concept `state.sessionStartDate` already represents); `"all"` is unfiltered; `"archive:{id}"` replays a closed season's own stored `manualBets` snapshot (Phase 23.1's Season Archive already keeps a full raw copy) through `mapRawManualBetsForStrategyLab()` — an adapter built entirely from existing utilities (`cleanString`, `normalizeDateString`, `normalizeMarket`, `calcProfitByResult`, `resultKey`), not a new computation.

- **Strategy Builder** — Opinion checkboxes (default STRONG BUY + BUY, matching what's actually followed in production), Minimum Analysis Score and Minimum Edge sliders, Odds min/max, an optional flat Stake override (powers "Units won" as the classic level-staking backtesting metric — omitted, it uses the strategy's own average real stake as the implicit unit), League/Market toggle chips (populated from whatever leagues/markets exist in the current pool), and the Season selector above. Every filter is optional and combines with AND logic in `applyStrategyLabFilters()`.
- **Historical Replay** (`computeStrategyReplay()`) — reuses `computeStreaks()` and `computeDrawdownAnalysis()` verbatim (the same functions History Intelligence/Bankroll Audit already use) for streaks and drawdown/recovery; Profit Factor, Expectancy, and Volatility are the only genuinely new (simple, one-line) formulas, since nothing else in the app already computes them.
- **Compare Against Production** — "Current Strategy" is the actual production baseline: the same `opinionBets` Opinion Validation already computed (cached in `window._opnSimCache`), filtered to `status !== 'rejected'` (what was really followed), replayed through the identical `computeStrategyReplay()`. Calibration/Decision Cost/Confidence for both sides reuse `window._opnSimCache`'s cached `calibrationScore()`/`statsFromBets()`/`confidenceTier()` functions — the exact same formulas Opinion Validation defined, applied to differently-bucketed data, never re-implemented. Arrow comparisons reuse `simCompareArrow()` (the same helper the Recommendation Simulator already defined).
- **Robustness Score (0–100)** — see the formula explanation below. Explicitly designed so a 5-bet/80%-ROI strategy can never outrank a 350-bet/18%-ROI one.
- **Stability** — the chronologically-sorted pool is split into three equal segments (First/Middle/Final Third); ROI is computed per segment (reusing the same stake/profit sum pattern as the main replay) and labelled Improving/Stable/Degrading (±10 points threshold between the first and last third).
- **Risk Analysis** — Max Drawdown €/%, Recovery Time, and both streak lengths come directly from the reused `computeDrawdownAnalysis()`/`computeStreaks()` results; Profit Factor, Expectancy, and Volatility (σ of per-bet profit) are computed once in the replay and simply displayed here.
- **Strategy Optimizer ("Best Nearby Strategy")** — bounded local search only: Opinion/League/Market/Odds are held fixed at the user's current selection; only Minimum Score (±20, 9 values) and Minimum Edge (±4pp, 9 values) are perturbed, ≤ 81 candidate evaluations, each ranked by Robustness Score (never raw ROI) so a degenerate tiny-sample candidate can never win. Candidates below 5 matching bets are discarded outright. Debounced 150ms into its own sub-container, matching the Recommendation Simulator's Best Nearby pattern.
- **Explainability** — `explainOptimizerSuggestion()` generates one sentence from real, computed deltas only (bet-count % change, Yield point change) — never a generic or assumed cause.
- **Export (JSON only, pure download)** — reuses the existing `downloadTextFile()` helper (the same one `exportManualJson()`/`exportRealCsv()` already use). The exported payload is built from `_stratLabLastResult`, the exact object the page just rendered from — export and display can never diverge.
- **Performance/caching** — league/market chip lists and the optimizer are the only parts recomputed per render; `_stratLabLastResult` doubles as both the render cache and the export data source. All replay stays in the browser; nothing is sent to any API.

**Robustness Score formula.** Four independently-bounded components summing to 0–100:
| Component | Range | Basis |
|---|---|---|
| Sample factor | 0–30 | Smooth curve over the same 10/20/50/100 confidence-tier breakpoints used everywhere else in this app |
| ROI factor | 0–30 | ROI clamped to `[-20%, +40%]` before scaling — ROI and Yield are the same information (`yield = roi/100`), so only ROI is scored to avoid double-weighting one signal; the clamp stops a small-sample outlier ROI from dominating |
| Consistency factor | 0–25 | Reuses `computeDrawdownAnalysis()`'s own `riskScore` (0–100), which already blends drawdown depth, recovery time, equity-curve smoothness, and sample size |
| Confidence factor | 0–15 | A small extra nudge from the tiered confidence label (Very Low=0 … Very High=15) |

Because the sample and consistency factors are both driven primarily by sample size, a tiny sample is doubly penalised regardless of how extreme its ROI is — this is what guarantees the required ordering property (verified in testing: 5 bets/80% ROI scores below 350 bets/18% ROI in every tested scenario).

## 12. Dashboard Refresh Model

### Automatic refresh — CSV data (60 seconds)

```
setInterval(60s)
  └─ loadData(true)
      ├─ fetches picks_hoje_github.csv
      ├─ fetches picks_btts.csv
      ├─ fetches picks_history.csv
      ├─ fetches manual_bets.csv (empty)
      └─ fetches fixtures_today.csv
      → state.footballDaily, state.footballHistory updated
      → rerenderAll()

  └─ checkPendingAlerts()
      └─ sends Telegram if any bot pick ≤ 30 min to kickoff
```

Does **not** refresh `state.manualBets`. Manual bet state is not part of the 60-second cycle.

### Automatic cloud save (4-second debounce)

```
Any state mutation
  └─ markDirty()
      └─ setTimeout(4000ms)
          └─ saveCloudState() → POST /save → Railway → GitHub
```

If a new mutation arrives within the 4 seconds, the timer resets. Only one save fires per burst of edits.

### Manual cloud reload

```
User clicks "Load Cloud"
  └─ _doLoadCloudState({ fromUser: true })
      └─ GET /load → Railway → GitHub → cloud_state.json
      └─ state.manualBets, bankrollInicial, localEdits, sessionStartDate ← cloud
      └─ saveLocalState()
      └─ rerenderAll()
```

Season recency guard: if the cloud `sessionStartDate` is older than the local one, the load is blocked with an alert.

### Post-settlement cloud reload

```
User clicks "Run Settlement"
  └─ POST /run-settlement → Railway (synchronous, up to ~90s)
      └─ settlement result returned
  └─ _reloadManualBetsFromCloud()
      └─ GET /load → Railway → cloud_state.json
      └─ state.manualBets ← content.manualBets
      └─ saveLocalState()
      └─ rerenderAll(false)
```

This is the only automatic cloud refresh that is not user-initiated. It happens only when settlement is triggered from the current browser session.

### Rendering refresh

`rerenderAll()` is called:
- After `loadData()` completes (every 60 seconds).
- After any `state` mutation via user action.
- After `_doLoadCloudState()` or `_reloadManualBetsFromCloud()` completes.
- After tab activation for Live Center, Daily Picks, and Pending (targeted renderer only).
- On window resize (debounced to 150ms).

## 13. Error Handling

### Network failures — CSV fetch

`loadData()` wraps all fetches in a try-catch. If `picks_history.csv` fails to load, the entire `loadData()` call fails (it is the required file; all others are optional).

`_loadDataFailCount` tracks consecutive failures. `_setFetchBanner()` shows a red banner when count ≥ 1:
- 1–2 failures: "Última atualização falhou. Nova tentativa em breve."
- 3+ failures: "Não foi possível atualizar os dados após várias tentativas."

The banner is cleared on the next successful `loadData()`.

### Network failures — cloud save

`saveCloudState()` catches errors and leaves `hasPendingCloudChanges = true`. The cloud status indicator shows "alterações por guardar". A retry is scheduled in the `finally` block. The in-memory state is not rolled back — user edits are safe in localStorage even if the cloud save fails.

### Railway unavailable

- Cloud status indicator shows "Cloud: indisponível".
- The "Load Cloud" button will show an error alert.
- The "Run Settlement" button will fail and show the error message.
- All CSV data (bot picks, history) continues to load from GitHub raw URLs unaffected.
- Manual bets remain visible from localStorage.

### GitHub unavailable

- `loadData()` fails. CSV data is not refreshed. The fetch error banner is shown.
- `saveCloudState()` fails (Railway cannot reach GitHub). The save is queued for retry.
- The dashboard remains functional with stale data from the last successful load.

### Malformed data

- `parseDelimitedCsv()` handles BOM, mixed delimiters (auto-detects `;` vs `,`), and quoted fields.
- `normalizeBotCsvRow()` and `normalizeManualCsvRow()` apply field normalisation and defaults.
- Rows with missing `Data` or `Jogo` are filtered out after parsing.
- JSON parse errors in `loadLocalState()` default the affected field to `[]` or `{}`.

### Missing files

- If `picks_hoje_github.csv` is missing or empty, `state.footballDaily` is set to `[]`. The Daily Picks page shows no picks (no error).
- If `league_stats.csv` is missing, `state.leagueStats` remains `[]`. League Analytics shows no data.
- If `fixtures_today.csv` is missing, `state.fixtures` is `[]`. Scout kickoff lookup returns null; the bet can still be created without kickoff data.

## 14. UI Design Principles

**Single-page application, no framework.** The entire dashboard is one HTML file. There is no React, Vue, Angular, or any other UI framework. There is no npm, no bundler, no transpiler. A change to the frontend is a change to `index.html`.

**All JavaScript is inline.** The `<script>` block at the bottom of `<body>` contains all application logic. There are no external JS files. This makes the dashboard self-contained and deployable without a server.

**Dark theme by default.** The CSS uses custom properties (`--bg`, `--card`, `--text`, etc.) defined on `:root`. The palette is a dark navy (`#0a0f1e`) with blue accents (`#3b82f6`). Color-coded states: green (`--ok`) for wins, red (`--bad`) for losses, amber (`--warn`) for warnings, blue (`--info`) for neutral.

**Deterministic rendering.** Every render function reads from `state` and produces HTML. There is no two-way binding, no reactive system, no virtual DOM. Given the same `state`, the same HTML is always produced. This makes rendering predictable and debuggable.

**Mobile-responsive.** `isMobileDashboard()` checks viewport width (≤ 1024px). Mobile views use card layouts instead of tables. The sidebar collapses to a hamburger menu on mobile. `setActiveTab()` and `rerenderAll()` both account for the active viewport.

**PT-PT user interface.** All user-facing text is in Portuguese (Portugal). Field labels, alert messages, button text, and status indicators are all in Portuguese. Internal variable names and code comments are in English.

**Defensive rendering.** Every render call in `rerenderAll()` is wrapped in a try-catch with a `console.error` fallback. A JavaScript error in the Analytics panel does not crash the Daily Picks panel. Each section fails independently.

**Auto-save over manual save.** The user never explicitly clicks "Save". State mutations trigger `markDirty()`, which schedules a debounced auto-save. The cloud status indicator communicates the save state transparently. If the save fails, the indicator remains amber and a retry is attempted.

**No duplicated persistence.** `state.manualBets` is the single in-memory representation of manual bets. It is written to localStorage by `saveLocalState()` and to GitHub by `saveCloudState()`. There is no third copy. When the cloud is loaded, `state.manualBets` is replaced entirely — not merged.

**Inline Poisson model.** The Scout workspace runs the Poisson model in the browser in JavaScript. No round-trip to the backend is needed for analysis. The model uses `state.fixtures` (downloaded from GitHub raw URL) for λ values.
