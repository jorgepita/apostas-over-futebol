**Phase 26.34 (this phase) fixed a manual-result-override precedence flaw.** A read-only investigation into a reported inconsistency ("Huntsville City vs Crown Legacy" showing `Result = P` in the dashboard while `picks_history.csv` was completely empty) found the underlying mechanism working as intended for that specific fixture, but uncovered a genuine design flaw in `getRowWithLocalEdits()`: a bot pick's manual result override (`localEdits.resultadoManual`, set via the History page's dropdown or "Live Settle") permanently took precedence over the CSV's own `Resultado`, with no reconciliation once automated settlement later determined a real result. A systematic scan of every historical override against the current CSV found this had already caused **two real, live bankroll/ROI misstatements** — "Saint Etienne vs Nice" and "Nice vs Saint Etienne" were both displaying a stale manual result that disagreed with what automated settlement had since determined. `getRowWithLocalEdits()` and `getDailyRowsMerged()`'s cross-file reconciliation now both prefer the CSV whenever it has a valid result, falling back to the manual override only while the CSV is still empty — automated settlement is now unconditionally the final source of truth once it exists. No automatic deletion of stale overrides (evaluated and rejected as unnecessarily risky for a function called on every render); they're simply never read again once superseded. Both misstated bets now show their correct result; the legitimate bridge case (Huntsville, whose automated settlement never resolves) is unaffected. See ADR-015 and Phase 26.34 in `08_Change_Log.md`.

**Phase 26.35 (this phase) fixed the Phase 26.33 StakeReal auto-fill guard.** A read-only investigation into a reported divergence — one approved bot pick correctly received its "Stake rec." default while a comparable one ("Mjallby AIF vs Vasteras SK FK") showed `StakeReal = €0.00` and did not contribute to Open Exposure — found the guard used string truthiness (`!existingStakeReal`) to decide whether a pick already had a real stake. A stored `stakeReal: "0"` (confirmed present in the live `cloud_state.json` for the affected pick) is a non-empty string, so the guard treated it identically to a deliberately-typed value and never replaced it, understating that pick's exposure indefinitely — including across an approve→cancel→re-approve cycle, since `pendingCancel()` deliberately preserves `stakeReal` on cancel. The guard now parses the value with the existing `num()` helper and auto-fills whenever it is `null` or `<= 0` (empty, undefined, invalid string, zero, or negative), leaving any genuine positive value untouched. `computeRecommendedStake()` — which can never legitimately return zero itself, by its own hard floor — exposure calculation, and bankroll calculation are all byte-identical to before this phase. See `05_Known_Issues.md` DASHBOARD-5 and Phase 26.35 in `08_Change_Log.md`.

Manual bet rows are completely unaffected — they have no model/recommended/real distinction. `computeRecommendedStake()` itself, exposure calculation, bankroll calculation, settlement, persistence, and StakeReal behaviour are all unchanged. See Phase 26.36 in `08_Change_Log.md`.

**Phase 26.38 implemented the first fix from the completed Performance Audit.** The audit measured `rerenderAll()` — which fires on every Approve, Cancel, and inline edit — at **87.7 seconds** on the real production account, and traced 97% of that cost to four functions, three of which (`renderAlertsCenter()`, `renderSummaryHeadlineStats()`, `renderMobileHomeDash()`) call `getPendingRows()` purely for `.length`. Since Phase 26.36, every bot row inside `getPendingRows()` calls `computeRecommendedStake()`, cascading into `getRiskMetrics()`/`getMetrics()` and roughly 9 full history/manual-bet-array rebuilds per pending row — with 271 approved picks in the real account, this made every count-only call as expensive as the Pending page's own legitimate render. A new, minimal `getPendingCount()` helper mirrors `getPendingRows()`'s two filter predicates but stops at `.length`, never calling `computeRecommendedStake()` or building row objects; the three count-only call sites now use it. `getPendingRows()` itself and `renderPendingQueue()` (the Pending page's own renderer) are byte-for-byte unchanged — confirmed via `getPendingCount() === getPendingRows().length` before and after Approve/Cancel mutations, and via the full 10-suite regression harness. Measured: `rerenderAll()` 87.7s → 28.7s (-67.3%); `renderAlertsCenter()` 23.7s → 1.10s (-95.4%); `renderSummaryHeadlineStats()` 18.9s → 0.28s (-98.5%); `renderTopDecisionBlock()` 17.5s → 1.09s (-93.8%). `renderPendingQueue()`/`rerenderManualOnly()` were unchanged by design (~15–20s) and became the single largest remaining cost. See Phase 26.38 in `08_Change_Log.md`.

**Phase 26.39 (this phase) implemented the audit's second fix: a shared data-layer memoization cache.** `renderPendingQueue()`'s residual cost was never about `getPendingRows()` itself being slow — it was that `computeRecommendedStake()` (called once per pending bot row, ~27 rows on the real account) triggered `getStakeContext() → getRiskMetrics() → getMetrics()`, and none of that chain was cached, so every row re-did the same ~9 full array rebuilds. A dependency audit confirmed 8 of the 9 functions in that chain (all but `computeRecommendedStake()` itself, which takes an external row parameter) are pure functions of `state` for a fixed generation, with no dependency on the current time — safe to cache; `getPendingRows()`/`getPendingCount()` were deliberately excluded, since they additionally depend on `Date.now()`. One shared cache (`_dataCache` + a single `_dataGeneration` counter, via `memoizeDataFn()`) now covers `getHistoryRowsMerged`, `getDailyRowsMerged`, `getAllBotRowsMergedUnique`, `getManualRowsMerged`, `getResolvedManualBets`, `getMetrics`, `getRiskMetrics`, and `getStakeContext`. Every state mutation invalidates it: `markDirty()` (covering the majority of local-edit paths) plus 13 explicitly-added calls at the mutation functions that don't go through `markDirty()` (CSV reload, cloud load/reload, JSON import, bankroll movement add/delete, Settings resets, season close, initial-bankroll inputs) — found by reading every assignment to the 7 relevant `state` containers, not assumed. Measured: `renderPendingQueue()` 18.8s → 0.11s (-99.4%); `rerenderAll()` 28.7s → ~1.1–1.2s (-96%); combined with Phase 26.38, over **98% faster** than the original 87.7s audit baseline. Full 11-suite regression harness (including a new 10-check cache-correctness suite covering Approve/Cancel/Stake edit/Odd edit/manual create/delete/settlement/cloud reload) all pass — no user-visible value changed. See Phase 26.39 in `08_Change_Log.md`.

## Completed Areas

**Pick generation.** GitHub Actions runs at 17:00 UTC (main) and 23:00 UTC (top-up for non-EU leagues). Poisson model generates O2.5 and BTTS picks across 21 leagues. Picks are committed to GitHub and sent via Telegram.

**Bot pick approval (Phase 26.33, guard corrected Phase 26.35).** Approving a Daily Picks row ("Aprovar") defaults `StakeReal` to that row's "Stake rec." value (`computeRecommendedStake()`) whenever the existing value is not a meaningful positive stake — empty, undefined, invalid, zero, or negative — and never overwrites a genuine positive value the user (or a prior approval) already set. Applied at approval time, via the same `localEdits`/`markDirty()`/`saveLocalState()` pipeline every other bot-pick edit already uses — no new persistence path. Phase 26.33's original guard used string truthiness and could be permanently defeated by a stored `"0"`; Phase 26.35 replaced it with a parsed-numeric check — see `05_Known_Issues.md` DASHBOARD-5.

**Bot pick result precedence (Phase 26.34).** A bot pick's manual result override (`localEdits.resultadoManual`) is now strictly a temporary bridge: `getRowWithLocalEdits()` and `getDailyRowsMerged()` always prefer a valid CSV `Resultado` once one exists, falling back to the manual override only while the CSV is still empty. This closed a real gap where a stale manual override could permanently mask a later, correct automated result — see `05_Known_Issues.md` DASHBOARD-4 and ADR-015.

**Shared Quantitative Engine (Phase 26.29, closed Phase 26.30).** `src/calculations.py` is the canonical implementation of every quantitative calculation (lambda projection, per-league lambda-boost, model probability, implied probability, edge, Kelly, confidence, fair odds, expected value); `QuantEngine` in `index.html` is a verified JavaScript mirror consumed by the Manual Bet Scout. Both are held numerically identical by a golden-vector conformance test suite rather than shared source (not possible given ADR-005's no-build-step constraint) — 16 functions, 142 Python / 285 JS assertions. No quantitative formula duplication remains inside the Bot + Scout architecture. See `04_Backend.md` §15 and ADR-014.

**Settlement.** Runs at 07:00 and 22:30 UTC via GitHub Actions, and on demand via the dashboard. Bot picks and manual bets share the same `update_dataframe()` engine, including rejected manual bets — the engine does not filter by lifecycle status (Phase 26.19; see ADR-012). Both write sites now also capture the final score (`Placar`, e.g. `"2-1"`) alongside `Resultado`/`Lucro€`, for both bot picks and manual bets. football-data.org is the primary source for EU leagues; API-Football is used for blocked EU and all non-EU leagues. Both providers' responses are validated for embedded errors (plan/quota/auth/network/server) before being trusted, with the result surfaced in the settlement summary, dashboard, logs, and a persistent per-provider health record in `cloud_state.json` (Phase 26.18 — see `04_Backend.md` §7 and ADR-011). Fixture-backed manual bets (created from Scout) now persist `kickoffUTC`/`homeTeam`/`awayTeam`/`leagueId` at creation time (Phase 26.32), so the shared engine's `RESULT_READY_DELAY` eligibility gate applies to manual bets exactly as it already did to bot picks — closing a gap where a manual bet could settle before the bot pick for the identical fixture (see `05_Known_Issues.md` SETTLEMENT-2). Free-form manual bets (no fixture) are unaffected — a documented, accepted limitation, not a bug.

**Manual Bet lifecycle (Phase 26.19, corrected Phase 26.31).** A bet's lifecycle status and its settlement result are independent (ADR-012): `status` (`pending`/`approved`/`rejected`/`settled`) tracks the workflow decision; `resultado`/`placar` tracks what actually happened in the match. A rejected bet is settled by the same engine as any other bet but never advances to `status: 'settled'` and never affects bankroll, ROI, or any financial calculation (`getResolvedManualBets()` excludes it). Rejected bets remain visible in the operational Manual Bets list ("Apostas Manuais") only while unsettled — once settled, they drop out of that list automatically (Phase 26.31, correcting Phase 26.28's fix, which had targeted the wrong page). The History page's "Rejeitadas" view (`getRejectedManualBets()`) is the permanent archive: a rejected bet stays there forever, settled or not, and remains available to Strategy Lab, Opinion Validation, and every other analytical module.

**Duplicate manual bet prevention (Phase 26.19).** Three independent layers: (1) the Scout workspace hides a fixture's card the instant any bet exists for it, in any lifecycle state, not just once approved/rejected — the card only reappears if the bet is removed; (2) `findManualBetByOpportunity()` guards both the Scout create path and the manual entry form synchronously, so a double-click cannot create two records; (3) the backend (`POST /save` → `_dedupe_manual_bets()`) independently drops later duplicates for the same fixture+market before persisting to GitHub, as an authoritative backstop, and the frontend resyncs from the cloud if it ever has to (ADR-013).

**Railway backend.** Five endpoints operational (`/`, `/health`, `/load`, `/save`, `/run-settlement`). Stateless, single worker, 300-second timeout. `cloud_state.json` is the persistence bridge between browser and GitHub. `POST /save` now also deduplicates `manualBets` before writing (Phase 26.19).

**Dashboard.** All pages functional: Daily Picks, Live Center, Pending, Manual Bets, History (now with a Resolvidas/Rejeitadas toggle), Analytics, Bot vs Manual, Bankroll/Settings. Auto-save to cloud with 4-second debounce. Scout workspace with Poisson analysis for manual bet creation. The Pending page itself renders from `getPendingRows()`; the Pending KPI and the "Muitas apostas abertas" alert instead read from `getPendingCount()` (Phase 26.38) — a lightweight helper mirroring the same two filter predicates without the expensive per-row `computeRecommendedStake()` work — so the three are mathematically guaranteed to agree and still cannot numerically diverge. Pending's displayed "Stake" for bot rows is sourced from `computeRecommendedStake()` (Phase 26.36) — directly comparable to "Stake Real"; the desktop column header reads plain "Stake" (Phase 26.37, since the header is shared with manual rows), while the mobile card's per-row label still reads "Stake rec." for bot rows; manual rows are unaffected either way.

**Manual bet and bankroll cloud synchronization.** `cloud_state.json` is the authoritative source for both `manualBets` and `movements` (bankroll deposits/withdrawals). A fresh browser session (e.g. Incognito, a new device, or cleared localStorage) reconstructs the exact same runtime state — bankroll, movements, manual bets, pending/live classification, KPIs, alerts — as a session that already has local data.

**Synchronization model is event-driven, not polling-based.** The 60-second `setInterval` in `boot()` refreshes only the read-only picks CSVs (`loadData()`), league stats, and pending-alert checks. It never re-fetches `cloud_state.json` and never touches `state.manualBets` or `state.movements`. Manual bets and movements are instead refreshed on explicit events: boot (`_doLoadCloudState()` / `_reloadManualBetsFromCloud()`), on-demand settlement completing, the "Load Cloud" button, tab visibility change, and now also whenever a save drops a server-side duplicate (`duplicatesRemoved` in the `/save` response — Phase 26.19).

**Telegram notifications.** New picks sent after each generation run with deduplication via `sent_state.json`.

**League registry.** 21 leagues managed via `src/league_registry.py`. All settlement routing derived automatically.

**Opinion analytics suite (Phases 26.20–26.23, Bot vs Manual tab).** Below the existing Opinion Performance/Calibration/Insights sections: **Opinion Validation** — expected-vs-actual ranking, a weighted-pairwise Calibration Score (0–100) with a configurable tolerance for insignificant inversions, an Opinion Pair Analysis table, a Decision Cost metric, per-opinion trend sparklines, a sample-size Confidence indicator, ranked insights, a trend warning, and a calibration-over-time chart. **Opinion Engine Recommendations** — a deterministic (non-AI) rule engine over that same analytics, producing severity-ranked, evidence-backed recommendations and one overall Opinion Engine Health label. **Recommendation Simulator** — a pure what-if layer (three sliders, ephemeral, never persisted) that replays settled opinion bets through a parameterized copy of the real classifier, with a bounded (≤1331-combination) "Best Nearby Configuration" search. All three are analytics-only and read-only; see `03_Dashboard.md` §10 for full technical detail and ADR references.

**Strategy Lab (Phase 26.24, own tab).** A frontend-only betting-strategy backtester, distinct from the Opinion analytics above: a Strategy Builder (opinion/score/edge/odds/stake/league/market/season filters) feeds a Historical Replay, a Compare-Against-Production panel, a Robustness Score explicitly designed so tiny samples can never outrank large ones, chronological-thirds Stability, Risk Analysis, a bounded (≤81-combination) Strategy Optimizer, and a pure JSON export. No persistence, no writes to production state. See `03_Dashboard.md` §10.

Internal English status/severity codes used in rule-engine comparisons (e.g. `'Broken'`, `'HIGH'`, `'PROMOTE'`) are unchanged — only translated at render time via a shared `ptLabel()` lookup — so no comparison logic, threshold, or persisted value changed.
