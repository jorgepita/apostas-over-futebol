**Phase 26.45 (this phase) implemented Policy A, the fixture-level bot-pick market lock**, closing a cross-run gap a prior read-only lifecycle investigation confirmed had already produced two real production duplicates: West Ham vs Leeds (O2.5 persisted 2026-05-20, BTTS persisted ~24h later, across ≥8 intervening runs where only O2.5 existed; both markets subsequently show `apostada:true` with identical real stake/odd in `cloud_state.json["localEdits"]`) and Gnistan vs Mariehamn (O2.5 persisted 2026-07-07, BTTS ~4 days later). Root cause: `dedupe_correlated_picks()` correctly picks one market per fixture *within a single generation run*, but every persisted identity downstream (`picks_history.csv`, `localEdits`, settlement, `sent_state.json`) is market-specific — nothing prevented a later run's re-evaluation of the same fixture (across the rolling multi-day generation window, or between the 17:00 main and 23:00 top-up jobs) from persisting the competing market if the Edge ranking flipped. Fixed via a new `apply_fixture_market_lock()` (`src/pipeline.py`), which runs on the concatenated O2.5+BTTS candidate set *before* the unchanged same-run `dedupe_correlated_picks()` selection: once a fixture has any bot market in `picks_history.csv`, a candidate for a *different* market is discarded before it can ever reach dedupe, staking, daily files, history, or Telegram — regardless of whether the existing pick is unapproved, approved with real stake, cancelled, settled W/L/P, or voided. Regenerating the *same* market is unaffected. One shared call site in `main.py`'s `main()` covers both the main and top-up jobs identically — no second implementation. Bot-only (manual bets untouched); the two historical duplicates are left exactly as they are — this fix is preventative, not retroactive. Zero change to settlement, ADR-015's CSV-wins precedence, ADR-017's void policy, MLS/MLS Next Pro routing, `league_stats.csv` persistence, or any dashboard code — `index.html` was not modified. 37 new tests (fixture-id normalization/equivalence, direct lock behaviour across every approval/settlement/void state, cross-run flips on both generation paths, rolling multi-day re-evaluation, MLS/MLS Next Pro independence); full suite 299/299 passing; QuantEngine golden vectors 285/285 (unaffected, as expected). See ADR-018, `05_Known_Issues.md` GENERATION-1, and Phase 26.45 in `08_Change_Log.md`.

**Phase 26.43 closed the postponed-fixture lifecycle gap flagged in Phase 26.42's "Next Priorities".** A bet could previously remain open forever once its fixture was postponed/cancelled/abandoned or became undiscoverable (Chicago Fire vs Vancouver Whitecaps, 2026-07-17, was the concrete case) — the settlement engine correctly never settled it *incorrectly*, but also never resolved it any other way. **Phase 26.34 (this phase) fixed a manual-result-override precedence flaw.** A read-only investigation into a reported inconsistency ("Huntsville City vs Crown Legacy" showing `Result = P` in the dashboard while `picks_history.csv` was completely empty) found the underlying mechanism working as intended for that specific fixture, but uncovered a genuine design flaw in `getRowWithLocalEdits()`: a bot pick's manual result override (`localEdits.resultadoManual`, set via the History page's dropdown or "Live Settle") permanently took precedence over the CSV's own `Resultado`, with no reconciliation once automated settlement later determined a real result. **Phase 26.35 (this phase) fixed the Phase 26.33 StakeReal auto-fill guard.** A read-only investigation into a reported divergence — one approved bot pick correctly received its "Stake rec." default while a comparable one ("Mjallby AIF vs Vasteras SK FK") showed `StakeReal = €0.00` and did not contribute to Open Exposure — found the guard used string truthiness (`!existingStakeReal`) to decide whether a pick already had a real stake. A stored `stakeReal: "0"` (confirmed present in the live `cloud_state.json` for the affected pick) is a non-empty string, so the guard treated it identically to a deliberately-typed value and never replaced it, understating that pick's exposure indefinitely — including across an approve→cancel→re-approve cycle, since `pendingCancel()` deliberately preserves `stakeReal` on cancel. **Phase 26.38 implemented the first fix from the completed Performance Audit.** The audit measured `rerenderAll()` — which fires on every Approve, Cancel, and inline edit — at **87.7 seconds** on the real production account, and traced 97% of that cost to four functions, three of which (`renderAlertsCenter()`, `renderSummaryHeadlineStats()`, `renderMobileHomeDash()`) call `getPendingRows()` purely for `.length`. Since Phase 26.36, every bot row inside `getPendingRows()` calls `computeRecommendedStake()`, cascading into `getRiskMetrics()`/`getMetrics()` and roughly 9 full history/manual-bet-array rebuilds per pending row — with 271 approved picks in the real account, this made every count-only call as expensive as the Pending page's own legitimate render. A new, minimal `getPendingCount()` helper mirrors `getPendingRows()`'s two filter predicates but stops at `.length`, never calling `computeRecommendedStake()` or building row objects; the three count-only call sites now use it. `getPendingRows()` itself and `renderPendingQueue()` (the Pending page's own renderer) are byte-for-byte unchanged — confirmed via `getPendingCount() === getPendingRows().length` before and after Approve/Cancel mutations, and via the full 10-suite regression harness. Measured: `rerenderAll()` 87.7s → 28.7s (-67.3%); `renderAlertsCenter()` 23.7s → 1.10s (-95.4%); `renderSummaryHeadlineStats()` 18.9s → 0.28s (-98.5%); `renderTopDecisionBlock()` 17.5s → 1.09s (-93.8%). `renderPendingQueue()`/`rerenderManualOnly()` were unchanged by design (~15–20s) and became the single largest remaining cost. See Phase 26.38 in `08_Change_Log.md`.

**Phase 26.39 implemented the audit's second fix: a shared data-layer memoization cache.** `renderPendingQueue()`'s residual cost was never about `getPendingRows()` itself being slow — it was that `computeRecommendedStake()` (called once per pending bot row, ~27 rows on the real account) triggered `getStakeContext() → getRiskMetrics() → getMetrics()`, and none of that chain was cached, so every row re-did the same ~9 full array rebuilds. A dependency audit confirmed 8 of the 9 functions in that chain (all but `computeRecommendedStake()` itself, which takes an external row parameter) are pure functions of `state` for a fixed generation, with no dependency on the current time — safe to cache; `getPendingRows()`/`getPendingCount()` were deliberately excluded, since they additionally depend on `Date.now()`. One shared cache (`_dataCache` + a single `_dataGeneration` counter, via `memoizeDataFn()`) now covers `getHistoryRowsMerged`, `getDailyRowsMerged`, `getAllBotRowsMergedUnique`, `getManualRowsMerged`, `getResolvedManualBets`, `getMetrics`, `getRiskMetrics`, and `getStakeContext`. Every state mutation invalidates it: `markDirty()` (covering the majority of local-edit paths) plus 13 explicitly-added calls at the mutation functions that don't go through `markDirty()` (CSV reload, cloud load/reload, JSON import, bankroll movement add/delete, Settings resets, season close, initial-bankroll inputs) — found by reading every assignment to the 7 relevant `state` containers, not assumed. Measured: `renderPendingQueue()` 18.8s → 0.11s (-99.4%); `rerenderAll()` 28.7s → ~1.1–1.2s (-96%); combined with Phase 26.38, over **98% faster** than the original 87.7s audit baseline. Full 11-suite regression harness (including a new 10-check cache-correctness suite covering Approve/Cancel/Stake edit/Odd edit/manual create/delete/settlement/cloud reload) all pass — no user-visible value changed. See Phase 26.39 in `08_Change_Log.md`.

**Phase 26.40 (this phase) fixed two issues found during the Performance Audit's own validation work, then implemented the audit's third and final optimisation.** Issue A: `pendingCancel()` silently left the Daily Picks "Aprovar" button non-functional for a re-approval attempted in the same session — root-caused to `pendingCancel()` re-rendering the Daily Picks table without rebinding its click handlers (`bindBotTableControls()` was never called after the render it triggered); fixed by adding a `bindBotTableControls()` call at the end of `pendingCancel()`. Issue B: `addMovement()` and the delete-movement handler mutated `state.movements` (and therefore the bankroll) without calling `markDirty()` — a pre-existing quirk explicitly flagged as harmless-at-the-time in Phase 26.39's own notes, but one that left bankroll movements never triggering a cloud save or cache invalidation; fixed by replacing their standalone `invalidateDataCache()` calls with `markDirty()`, the same mutation-notification path every other state change already uses (confirmed the safest option — reusing an existing, well-tested hub rather than hand-rolling a second one). Both fixes validated with a new 12-check targeted Playwright script.

The audit's third fix (H3, unaddressed by H1/H2 by design) targeted the remaining rendering-architecture cost flagged in this document's own prior "Next Priorities": `rerenderAll()` was still unconditionally rebuilding ~50 render functions' DOM regardless of which single tab was visible, and one logical action (e.g. Approve) could trigger two overlapping full render passes. **H3.1** introduced `renderActiveTabIfStale()`, a generation-aware dedup guard (reusing Phase 26.39's `_dataGeneration` counter) that skips a second render of the same tab against unchanged data — called consistently from `markDirty()`, `rerenderAll()`, and `setActiveTab()`, so back-to-back calls for one click no longer both do full work. **H3.2** replaced unconditional full-page rendering with `PAGE_RENDERERS`, a dependency map (tab id → its own render functions) built from tracing each function's actual DOM target — not the old `rerenderXOnly()` groupings, several of which mixed multiple tabs together — dispatched by `renderActiveTabContent()`/`renderActiveTabIfStale()`. Every tab panel remains fully mounted in the DOM and instantly current the moment it's activated (`setActiveTab()` always forces a fresh render on switch) — **this is not lazy-loading**, only redundant work on invisible tabs was eliminated. `renderVersus()` was kept as one deliberate, documented GLOBAL exception (populates `window._opnSimCache`, needed by Strategy Lab/Recommendation Engine/Opinion Validation/Simulator regardless of active tab; cost ~0.18–0.22s, negligible). A live-input regression was caught and fixed during validation: rendering the active tab on every keystroke in the Pending page's Odd Real/Stake Real fields destroyed the input being edited — `markDirty(skipRender)` and `update(..., skipActiveTabRender)` parameters now let those two handlers skip the immediate re-render while still invalidating the cache and scheduling the cloud save. Measured on the real production account: `rerenderAll()` (fresh generation) ~177ms, Approve ~224ms, Cancel ~201ms — down from Phase 26.39's ~1.1–2.7s and the original 87.7s baseline (over 99.8% faster in total). Page navigation after H3.2 costs only that destination page's own render (10–350ms depending on page weight) instead of a full `rerenderAll()`; re-visiting an already-current tab costs ~2ms (dedup path). See ADR-016 and Phase 26.40 in `08_Change_Log.md` for full detail, including the complete Before/H1/H2/H3 timing table.

## Completed Areas

**Pick generation.** GitHub Actions runs at 17:00 UTC (main) and 23:00 UTC (top-up for non-EU leagues). Poisson model generates O2.5 and BTTS picks across 22 leagues (Phase 26.42 added MLS Next Pro as a fully independent 22nd league). Same-run cross-market selection (`dedupe_correlated_picks()`, unchanged) picks one market per fixture by highest Edge; since Phase 26.45, a fixture-level lock (`apply_fixture_market_lock()`, ADR-018) additionally prevents a *later* run from ever persisting the competing market for a fixture that already has a bot recommendation. Picks are committed to GitHub and sent via Telegram.

**Bot pick approval (Phase 26.33, guard corrected Phase 26.35).** Approving a Daily Picks row ("Aprovar") defaults `StakeReal` to that row's "Stake rec." value (`computeRecommendedStake()`) whenever the existing value is not a meaningful positive stake — empty, undefined, invalid, zero, or negative — and never overwrites a genuine positive value the user (or a prior approval) already set. Applied at approval time, via the same `localEdits`/`markDirty()`/`saveLocalState()` pipeline every other bot-pick edit already uses — no new persistence path. Phase 26.33's original guard used string truthiness and could be permanently defeated by a stored `"0"`; Phase 26.35 replaced it with a parsed-numeric check — see `05_Known_Issues.md` DASHBOARD-5.

**Bot pick result precedence (Phase 26.34).** A bot pick's manual result override (`localEdits.resultadoManual`) is now strictly a temporary bridge: `getRowWithLocalEdits()` and `getDailyRowsMerged()` always prefer a valid CSV `Resultado` once one exists, falling back to the manual override only while the CSV is still empty. This closed a real gap where a stale manual override could permanently mask a later, correct automated result — see `05_Known_Issues.md` DASHBOARD-4 and ADR-015.

**Shared Quantitative Engine (Phase 26.29, closed Phase 26.30).** `src/calculations.py` is the canonical implementation of every quantitative calculation (lambda projection, per-league lambda-boost, model probability, implied probability, edge, Kelly, confidence, fair odds, expected value); `QuantEngine` in `index.html` is a verified JavaScript mirror consumed by the Manual Bet Scout. Both are held numerically identical by a golden-vector conformance test suite rather than shared source (not possible given ADR-005's no-build-step constraint) — 16 functions, 142 Python / 285 JS assertions. No quantitative formula duplication remains inside the Bot + Scout architecture. See `04_Backend.md` §15 and ADR-014.

**Settlement.** Runs at 07:00 and 22:30 UTC via GitHub Actions, and on demand via the dashboard. Bot picks and manual bets share the same `update_dataframe()` engine, including rejected manual bets — the engine does not filter by lifecycle status (Phase 26.19; see ADR-012). Fixed by extending `HISTORY_COLUMNS` to mirror `update_results.py`'s `CSV_COLUMNS` exactly (plus a companion fix in `src/pipeline.py`'s `save_all_outputs()`, a second consumer that would otherwise raise `KeyError`) — preventative only, does not reconstruct the already-lost historical `Placar` values (see `05_Known_Issues.md` SETTLEMENT-4). The audit also corrected this document's own Chicago Fire projection: `MissingAttempts` starts at 0 the first time the new policy actually runs against a row (the live file has no such column yet), so it will **not** auto-void on the first settlement run — it needs `missing_fixture_min_attempts` (3) separate genuine-`NO_MATCH` runs first, roughly 1.5 days at the normal twice-daily cadence, before the bounded rediscovery search and a possible void can happen at all. 9 new Python tests (`tests/test_history_schema.py`) plus the SUSP/INT test corrections bring the full suite to 253 passing; the manual-bridge Playwright regression (`test_settlementreason_bridge.js`, 17 checks) and the full pre-existing regression set were re-run with zero regressions. No production data was touched; no settlement was run.

**Phase 26.44 fixed the `league_stats.csv` upload gap** (see the "Overall Project Status" paragraph above for the full write-up; not repeated here).

**Phase 26.45 (this session) implemented the fixture-level bot-pick market lock (Policy A)**, following directly from a prior session's read-only lifecycle investigation into the O2.5-vs-BTTS market-selection architecture. That investigation reconfirmed `dedupe_correlated_picks()`'s same-run cross-market selection was already correct and unchanged, but found the real gap one level up: nothing prevented a *later* generation run from persisting the competing market for a fixture that already had a bot recommendation from an earlier run, because every persisted identity downstream of that selection (`picks_history.csv`, `localEdits`, settlement, `sent_state.json`) is market-specific, not fixture-specific. Two real production cases — West Ham vs Leeds and Gnistan vs Mariehamn — confirmed this had already happened, both as genuine cross-run duplications (the two markets were never in the same run's candidate set at the same time), with West Ham vs Leeds additionally showing both markets carrying identical real stake/odd in `cloud_state.json["localEdits"]`. The investigation weighed two remediation policies — Policy A (first persisted market is permanent) and Policy B (pre-approval re-evaluation) — and recommended Policy A given the current architecture's cost/benefit and the small settled-history sample available to justify Policy B's larger surface (a new recommendation-pointer concept, superseded-row semantics, a new Telegram message type, and cancel/re-lock audit-trail tracking the codebase does not currently have). This session implemented Policy A: `apply_fixture_market_lock()` (`src/pipeline.py`) builds a fixture-id → {persisted markets} map from `picks_history.csv` once per run and rejects any candidate whose market is not already in that set for its fixture, running immediately before the unchanged `dedupe_correlated_picks()` call so an unlocked fixture's same-run Edge comparison is completely untouched. One shared call site in `main.py`'s `main()` covers both the 17:00 UTC main run and the 23:00 UTC top-up run identically. The lock triggers purely from a row's existence in history — regardless of `Apostada`, `Resultado`, or `SettlementReason` — since approval/cancel state lives only in `cloud_state.json["localEdits"]`, a layer the generation pipeline never reads. Three new fixture-identity helpers were added to `src/history.py` (`fixture_id_from_parts()`/`_from_simple()`/`_from_candidate()`), with the pre-existing market-specific `history_pick_id_from_simple()` refactored to build on top of the new fixture-only helper rather than duplicating string construction — its output is byte-for-byte unchanged. The two historical production duplicates are explicitly **not** migrated, deleted, or altered — this fix is preventative only; `build_locked_fixture_markets()` naturally treats a fixture already holding both markets as locked-to-both, since there is no third market for either to flip to. Manual bets, settlement (`update_dataframe()`), ADR-015's CSV-wins precedence, ADR-017's void policy, MLS/MLS Next Pro routing, and every dashboard code path are untouched — `index.html` was not modified. Validated with 37 new tests (`tests/test_fixture_id.py`, `tests/test_fixture_market_lock.py`) covering fixture-id normalization/equivalence, direct lock behaviour across every approval/settlement/void state (unapproved, approved-with-stake, cancelled, W/L/P, manual_void/postponed_timeout/missing_fixture_timeout), cross-run flips on both the main and top-up paths, rolling multi-day re-evaluation, top-up daily-file non-duplication, MLS/MLS Next Pro independence, the legacy dual-market case (proving no retroactive migration), and source-level guards proving `main.py` calls the lock exactly once, unconditionally, and before `dedupe_correlated_picks()`. Full suite: 299/299 passing (262 pre-existing + 37 new); QuantEngine golden vectors 285/285 (unaffected, as expected for a Python-only change). See ADR-018, `05_Known_Issues.md` GENERATION-1, and Phase 26.45 in `08_Change_Log.md`. **This work is implemented and validated but deliberately left uncommitted, pending explicit approval, per the session's instructions.**
