This cost significant debugging time this session (a `[null]`-in-array symptom traced back through several false leads — a `let` vs `window` property confusion for `initialLoadDone`, and a suspected app-side rendering bug — before the actual cause was found). Any future test script for this dashboard must bundle multiple values into one object/array before crossing into `page.evaluate()`.
- `initialLoadDone` (boot-completion flag) is declared with `let`, not attached to `window` — a `page.waitForFunction(() => window.initialLoadDone)"` will silently and permanently return `undefined`; use the bare identifier (`() => initialLoadDone`) instead, since `page.evaluate()`/`waitForFunction()` execute in the page's global lexical scope, not just `window`'s own properties.

## Pre-Commit Duplication Audit (second pass, same date)

**Question posed:** can the exposure lookup (`getApprovedFixtureExposure()`) count the same logical approved bet more than once, because it appears through more than one collection/representation in dashboard state?

**Method:** traced the real data flow (not assumed) through `getAllBotRowsMergedUnique()` and `getManualRowsMerged()`, then wrote and ran a dedicated 29-check Playwright script (`test_exposure_duplication_audit.js`, scratchpad-only) empirically probing every legitimate multi-representation scenario before drawing a conclusion.

**Findings:**
- A bot pick legitimately exists in both `state.footballHistory` and `state.footballDaily` simultaneously — approval never removes the row from today's raw daily CSV, it only records `apostada` in `localEdits`. `getAllBotRowsMergedUnique()`'s pre-existing exact-`_pickKey` `Map` already collapses this to one entry, because both arrays are normalised through the identical `normalizeBotCsvRow()` and are written from the same generation-time string — confirmed with three separate JS object instances sharing one `_pickKey` collapsing to exactly one merged row.
- A manual bet has no equivalent dual representation: `state.manualBets` holds one mutable record per `id`, mutated in place across its lifecycle, never duplicated. The only other array `getManualRowsMerged()` merges in, `state.manualBetsRemote` (the dead `manual_bets.csv`, ADR-001, always empty in production), is excluded entirely via `isLocal === true` — confirmed by seeding a hypothetical non-empty remote row describing the identical fixture+market and observing zero contribution from it.
- Two genuinely distinct approved bot markets, and two genuinely distinct approved manual markets, on the same fixture are both correctly counted as two separate exposures (not collapsed).
- A settled bot bet (history) with a stale, still-unresolved daily-CSV copy of the same pick is correctly excluded — history's settled result wins, exactly as ADR-015 already establishes for display purposes generally.
- Every void variant (`postponed_timeout`, `missing_fixture_timeout`, `manual_void` — all just `Resultado: 'P'` plus a `SettlementReason` label, per ADR-017) is excluded identically to a plain `P`, for both bot and manual bets.
- The Phase 26.33/26.35 StakeReal auto-fill default still applies correctly (and is reflected in the warning) when a conflict triggers the dialog and the user confirms.

**Conclusion:** one logical bet cannot currently be counted more than once. **No production-code fix was required.** A small, additive code comment was added to `getApprovedFixtureExposure()` in `index.html` recording this verified guarantee, plus matching short notes in ADR-019's Consequences and `03_Dashboard.md`'s "Fixture-Level Approval Exposure Warning" subsection — so a future reader does not need to re-derive it. The Phase 26.46 Change Log entry and its summary-table row were both extended with a short paragraph describing this audit, following the same in-phase (not a new phase number) convention Phase 26.43's own pre-commit audit used.
