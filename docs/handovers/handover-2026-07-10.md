## Session Objective

Rework the Manual Bet lifecycle architecture (not just the UI): stop the Scout workspace from letting a user accidentally create a duplicate bet, add backend duplicate protection, stop treating "Reject" as deletion, cleanly decouple a bet's lifecycle status from its settlement result, add a Rejected History view, and confirm rejected bets flow through the existing shared settlement engine without duplicating any logic or persistence.

---

## Work Completed

**Two pre-existing defects found while implementing this (see `05_Known_Issues.md` MANUAL-1):**
- The Scout card hide-key excluded fixtures with a bet in `status ∈ {approved, rejected, settled}` — but not `pending`. A brand-new bet's card stayed visible/clickable until approved or rejected.
- `apply_df_results_to_manual_bets()` unconditionally set `status = 'settled'` on any bet that got a result, including already-rejected ones — silently erasing the rejection and letting it count in bankroll/ROI.

**Goal 1 — Scout duplicate prevention:** `renderManualScout()`'s `processedMatchKeys` now covers every bet in `state.manualBets` regardless of `status`. A card hides the instant Create succeeds, stays hidden across re-renders, and only reappears if the bet is removed.

**Goal 2 — Duplicate protection (frontend + backend):** `manualBetOpportunityKey()`/`findManualBetByOpportunity()` (reusing `normalizeLeagueCode()`/`normalizeMarket()`) guard both `addManualBetFromFixture()` (Scout) and `addManualBet()` (manual entry form) synchronously — a double-click cannot create two records. `sync_server.py` gained `_manual_bet_identity()`/`_dedupe_manual_bets()` (reusing `update_results._resolve_liga_display_name()`/`_normalize_market_code()`), wired into `POST /save`: keeps the earliest bet per `(data, liga, jogo, mercado)`, returns `duplicatesRemoved` in the response. `saveCloudState()` calls `_reloadManualBetsFromCloud()` when that's non-zero.

**Goal 3 — Reject preserves the bet:** Already true at the code level (`mbHandleRowReject()` only ever set `status: 'rejected'`, never spliced — the project's own docs had drifted from the implementation here and were corrected). What was actually missing was the backend guarantee (see Goal 4).

**Goal 4 — Lifecycle/settlement decoupling (ADR-012):** `apply_df_results_to_manual_bets()` now only advances `status` to `'settled'` when it wasn't already `'rejected'`. `getResolvedManualBets()` additionally excludes `status === 'rejected'` — the single choke point for bankroll/ROI/analytics/versus/KPIs. `getFilteredRealClosedRows()`'s manual branch now builds on `getResolvedManualBets()` instead of a separately-duplicated `_lucro !== null` filter.

**Goal 5 — Rejected History view:** History page's "Fechadas reais filtradas" card gained a Resolvidas/Rejeitadas toggle (`_historyViewMode`, transient/unpersisted). Rejeitadas (`renderRejectedHistoryTable()`/`getRejectedHistoryRows()`/`getRejectedManualBets()`) reuses the same card/filter-bar/table with a different `<thead>` and row-renderer: Data, Liga, Jogo, Mercado, Odd, Stake, Análise, Opinião, Placar Final, Resultado, Lucro Teórico, Notas.

**Goal 6 — Rejected bets settle through the same engine:** Confirmed `manual_bets_to_settlement_df()`/`update_dataframe()` never filtered by lifecycle status — this was already true. Added a new `Placar` (final score, e.g. `"2-1"`) column to `CSV_COLUMNS`, written at both settlement write sites (`try_update_row_via_api_football()` and the football-data.org branch), round-tripped through `manual_bets_to_settlement_df()`/`apply_df_results_to_manual_bets()`. Additive/backward-compatible; populated identically for bot picks (shared engine, no bot-specific branch).

**Goal 7 — Analytics compatibility:** Confirmed the bet object already carries everything needed for future rejected-bet metrics (league, market, opinion, analysis score, edge, resultado, lucro, and now placar) — no further schema change needed; no dashboard built (out of this session's scope, per the request).

**Final architecture verification (before commit):** Re-checked Scout visibility, CSV backward compatibility, settlement compatibility, and duplicate protection against the actual code (not just the earlier summary). Found and fixed one genuine, narrow gap: `SYNC_RESULT_COLUMNS` (used by `sync_daily_from_history()`, the bot-pick catch-up path) had not been updated to include `Placar`, so a bot pick's final score could settle in `picks_history.csv` but never reach `picks_hoje_simplificado.csv` via that specific catch-up path — and would never self-correct afterwards, since `update_dataframe()` skips rows already marked `W`/`L`/`P`. Fixed by adding `Placar` to `SYNC_RESULT_COLUMNS`; re-validated with a dedicated round-trip test plus the full existing suite and the manual-bet round-trip tests. No other defects found; everything else matched the intended design exactly.

## Architectural Decisions

**ADR-012 added** — "A Manual Bet's Lifecycle Status Is Independent From Its Settlement Result; Rejected Is a Terminal, Analytical Lifecycle State." Extends the existing (already partially separate) `status`/`resultado` fields rather than introducing a new field or a combined vocabulary (no `RejectedWin`/`RejectedLoss`).

**ADR-013 added** — "Duplicate Manual Bet Protection Lives in the Existing `/save` Endpoint, Not a New Create Endpoint." Consistent with ADR-001/ADR-008 (one write path for `manualBets`) and ADR-004/ADR-009 (reuse the settlement engine's own league/market normalisers instead of a second implementation).

No existing ADR was contradicted or reversed.

## Notes for the Next Session

- `update_results.py`'s `CSV_COLUMNS` gained a new column, `Placar` — placed between `Resultado` and `Lucro€`. Any code that hardcodes the CSV column order (rather than reading by header name, which is what this codebase does everywhere) would need updating; none was found.
- `apply_df_results_to_manual_bets()` has one new conditional: `if bet.get('status') != 'rejected': bet['status'] = 'settled'`. Do not revert this to an unconditional assignment — see ADR-012 for why.
- `getResolvedManualBets()` in `index.html` is the single choke point for "does this manual bet count financially" — it now excludes `status === 'rejected'` in addition to its existing `_lucro !== null` check. Any new financial aggregation over manual bets should build on this function (or on `getFilteredRealClosedRows()`, which now does), not re-implement the `_lucro !== null` filter directly.
- `sync_server.py`'s `_dedupe_manual_bets()` lazily imports from `update_results` (same pattern as the existing `/run-settlement` handler) — the first `/save` call in a Railway process's lifetime pays a one-time import cost (pandas etc.), subsequent calls are free (module caching).
- The Playwright browser binaries and the `node_modules` used for validation this session live entirely in the scratchpad temp directory, not in the repository — nothing was added to `requirements.txt`, `package.json` (none exists), or committed to the project.
- Flask/flask-cors/gunicorn were missing from the project's `.venv` (already declared in `requirements.txt` but not installed) and were installed into that venv this session to run `sync_server.py` locally for validation — this is a local environment fix, not a project dependency change.
